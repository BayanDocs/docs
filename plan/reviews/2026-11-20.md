## Summary for the owner

Most of what the first review asked for has been done, and done carefully. Fuzzing, which feeds a parser millions of malformed inputs to find crashes, now runs in CI on every pull request that changes a fuzzed parser and every night, with new targets for the engine's messages, configuration and recordings. A check in bayan-core's gate keeps the engine away from clocks, files, the network and the environment. Both interim parsers are gone. The desktop's tests and sanitizers now run against the real engine. Both apps recover from an engine failure in the same way, which the protocol now spells out. The web app's accessibility is checked automatically in three browsers, and the server sends exactly the web app's security headers. Of the first review's 30 findings, 6 are fixed, 8 are partly fixed and 14 are open, and 2 are handled privately. Six of the open ones wait for the Phase-0 gate, as planned. The section [What is in good shape](#what-is-in-good-shape) lists more.

This review adds one high, five medium and eight low findings. The ones that matter most:

1. **The two apps keep growing apart** (H8). The first review asked for one change to the engine protocol before the apps build more on its gaps (H5). That change has not been made, and the fixes since then added behavior to each app instead. The apps now send the engine different input for the same keystrokes, only the web app can paste, they limit the accessibility tree differently, and they react differently when the engine refuses to start a session. The rule for restarting a failed engine is written twice, in C++ and in TypeScript, and kept in step by a comment. The recommendation is to hold the protocol session now, and to have bayan-core ship test cases that both apps must pass.
2. **A change to the web app's security headers would not reach the server** (M13). The server now sends the same headers, but only the server checks that, against a copy; a change made in bayan-web passes both repositories' checks.
3. **Changes from other people will reach the collaboration library without automatic fuzzing** (M14). Its fuzz target is parked for now, and even when it runs it covers one of six ways in. This has to be settled before the first work package that imports other people's changes.
4. **The extra security review exists only on paper** (M15). [plan/07](../07-quality-security-testing.md#3-security-program) asks for a dedicated security review of changes to security-sensitive code, which each repository lists in its `CODEOWNERS` file. The orchestrated workflow has no such step, and the lists leave out, among others, the gates of bayan-core, bayan-server and this repository, the fuzzing code, several parsers and the web app's security code.
5. **The crate layers, and the line between Apache-2.0 and GPL code, are checked by review only** (M16). The architecture lists 24 crates still to come, over all phases, among them the Apache-2.0 protocol crate.
6. **Agent sessions work with tools six weeks old** (M17). The cloud environment still runs the setup script of 2026-10-05, so sessions check their work with other versions than CI, among them a Node.js without November's security release.

Five items are yours alone:

- paste the current [setup script](../../scripts/cloud-environment-setup.sh) into the cloud environment, and tick items 1a to 1c of the [owner checklist](../09-owner-checklist.md) (M17);
- apply the GitHub settings baseline (H1, issue [#15](https://github.com/BayanDocs/docs/issues/15)): this repository's rules still date from 2026-10-09, and the baseline has gained checks since;
- decide the license of the shared supply-chain checker (L2);
- run the deferred screen-reader and input-method passes before the accessibility work packages start (M9);
- say which age rule holds for container images, if the answer loosens the runbook (L18).

Everything else is work for agent sessions, mostly small.

## How to read this report

- **Severity.** *High*: breaks an Accepted ADR or a spec, or is a security weakness with a realistic path, and will spread into Phase-1 work if not fixed now. *Medium*: drift or a gap with limited reach, or missing tests for important behavior. *Low*: hygiene and documentation drift. Nothing found is exploitable through a released product, because nothing has been released and no user document reaches the parsers yet, so no finding is rated critical.
- **Size.** *S*: one small pull request, under a day. *M*: a few days, one work package. *L*: several work packages.
- **Known.** Whether the problem was already recorded somewhere (an ADR, a brief, a pull request's follow-ups, a code comment).
- **Numbering.** New findings continue the first review's numbers, so that each ID names one finding across both reports: H8 is the first new high finding, M13 the first new medium one and L12 the first new low one. The first review's findings keep their IDs in [their status table](#status-of-the-findings-of-2026-10-27).

## High

### H8. The shells keep diverging while the protocol work of H5 waits

**What we found.** The first review's [H5](2026-10-27.md#h5-the-engine-protocol-leaves-behavior-to-the-shells-and-they-already-decide-differently) asked for one contract-first change to the [engine protocol](../../specs/engine-protocol.md) before the shells build further on its gaps. Since then the spec has gained only §12.1, the shells' recovery policy (FU-7), and the [CORE-125 draft](../../workpackages/phase-1/core.md#core-125--engine-api-v1-for-viewing) a list of open questions. Meanwhile the follow-ups added policy to each shell, and the shells now differ in these places:

| Behavior | bayan-desktop | bayan-web |
|---|---|---|
| Which keys reach the engine | Every key but Tab, with its modifiers, so also Ctrl+=, Ctrl+−, Ctrl+0, Ctrl+A, Ctrl+V and the function keys; printable keys as both `input.key` and `input.text` ([documentcanvas.cpp:809](https://github.com/BayanDocs/bayan-desktop/blob/8e6fae45051a58ce7e445c55714d97f38b2a8304/src/canvas/documentcanvas.cpp#L809-L826)) | Twelve editing keys ([keys.ts:9](https://github.com/BayanDocs/bayan-web/blob/45bf42e02d5b40ae1cd661df807cadf76529d995/src/input/keys.ts#L9-L22)) and the manifest's shortcuts, of which the engine's manifest has six today ([manifest.rs:29](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-engine/src/manifest.rs#L29-L34)); printable keys as `input.text` only |

| Restarting a failed engine | The rule of spec §12.1, written in C++ ([restartallowance.h](https://github.com/BayanDocs/bayan-desktop/blob/8e6fae45051a58ce7e445c55714d97f38b2a8304/src/app/restartallowance.h#L8)) | The same rule, written in TypeScript ([recovery.ts](https://github.com/BayanDocs/bayan-web/blob/45bf42e02d5b40ae1cd661df807cadf76529d995/src/engine/recovery.ts)) |

Three details make this worse than a list of differences:

- **Part of the key difference is new.** The first review's H5 recorded that the shells forward different keys. FU-8 then followed its interim advice in the desktop alone, so Ctrl+=, Ctrl+− and Ctrl+0, which neither shell sent before, now reach the engine from the desktop only. One of the desktop's comments says that every key but Tab goes to the engine "as from the web shell" ([documentcanvas.cpp:810](https://github.com/BayanDocs/bayan-desktop/blob/8e6fae45051a58ce7e445c55714d97f38b2a8304/src/canvas/documentcanvas.cpp#L810)), which is not so, and a later session reading it would believe the shells agree.
- **The restart rule is logic that both shells need, written twice.** The two versions agree today, with parallel but different unit tests, and the only link between them is a one-way comment in the desktop: "The same numbers are in bayan-web's src/engine/recovery.ts; change the spec and both shells together".
- **Neither shell shows the update prompt** that [spec §5](../../specs/engine-protocol.md#5-handshake) step 3 requires after the error `unsupported_protocol_version`.

**Why it matters.**

- The protocol's first goal: "One contract for both shells, so behavior cannot drift" ([spec §1](../../specs/engine-protocol.md#1-goals)).
- [plan/03 §3](../03-architecture.md#3-repositories-and-their-boundaries): "If two shells would need the same logic, it belongs in core"; [ADR-0002](../../adr/0002-repository-topology-and-contracts.md) decision 6 forbids writing the same logic twice.
- [ADR-0014's amendment of 2026-10-12](../../adr/0014-web-shell.md#amendment-2026-10-12-results-of-the-web-002-validation-gate) gives the engine, not the shell, the matching of Ctrl against Command.
- DESK-101 and WEB-101 will build navigation, find, copy and paste on exactly these paths, and every follow-up that adds shell policy without the contract adds another difference to undo later.

**Known:** mostly. The first review's H5 recorded the difference in key forwarding, and listed clipboard bytes as a gap and "which key presses a shell forwards" as an item for the protocol session; CORE-125's open questions record the accessibility limits and what a shell does after a protocol violation. New, and recorded nowhere: Ctrl+=, Ctrl+− and Ctrl+0 reaching the engine from the desktop only, the desktop's comment that claims parity, the `v` check and the missing update prompt.

**Recommended fix.**

**S, now (both shells and docs):**

- correct the desktop's comment about key parity, and give `recovery.ts` the reciprocal of `restartallowance.h`'s comment;
- add the unrecorded differences to CORE-125's open questions.

**M, before DESK-101 and WEB-101 are refined:** hold H5's protocol session now, as a planning task of its own rather than as part of the Phase-0 gate, with these items added to H5's list. With it:

- **conformance vectors** in bayan-core: test cases with their expected results, shipped as JSON next to the schema in the C SDK and the WebAssembly package, which both shells' unit tests read. They would cover restart sequences, tile-grid cases, accessibility-limit cases, and a table of which keys a shell forwards;
- consider moving the restart allowance into core's bindings, which already restart the engine after a panic ([spec §3.2](../../specs/engine-protocol.md#32-the-web-transport)) and already have a monotonic clock ([spec §10](../../specs/engine-protocol.md#10-record-and-replay)), so that the rule exists once.

### M13. Header drift between bayan-web and the server is caught only on the server's side

**What we found.**

- FU-2 made the server's headers equal to bayan-web's ([headers.rs:17](https://github.com/BayanDocs/bayan-server/blob/db0b20432946ae0eb9cb50f93ee6774cd982fe04/crates/bayan-server/src/http/headers.rs#L17-L37)); a comparison made for this review confirms that all eight are identical today. The server's test checks them against a copy taken by hand from bayan-web at `01c5978` ([tests/http.rs:14](https://github.com/BayanDocs/bayan-server/blob/db0b20432946ae0eb9cb50f93ee6774cd982fe04/crates/bayan-server/tests/http.rs#L14-L32)).
- Nothing on bayan-web's side knows about that copy. Its AGENTS.md says that the headers "have one source" and names only the nginx copy ([AGENTS.md:29](https://github.com/BayanDocs/bayan-web/blob/45bf42e02d5b40ae1cd661df807cadf76529d995/AGENTS.md#L29)); nothing in bayan-web mentions the server, and no workflow compares the two repositories (L10).
- So a change to bayan-web's headers passes both repositories' checks while the default deployment, the server serving the web app ([ADR-0015](../../adr/0015-server-architecture.md) decision 2), keeps sending the old set: the first review's H4 again. The server's AGENTS.md says that "drift on either side fails the test or shows in review" ([AGENTS.md:64](https://github.com/BayanDocs/bayan-server/blob/db0b20432946ae0eb9cb50f93ee6774cd982fe04/AGENTS.md#L64)), which holds only for a change on the server's side. WEB-103 will change the headers.
- The same line of bayan-web's AGENTS.md, and the comment at [security-headers.ts:26](https://github.com/BayanDocs/bayan-web/blob/45bf42e02d5b40ae1cd661df807cadf76529d995/config/security-headers.ts#L26), say that a further Trusted Types policy needs "an approved work package"; ADR-0014's amendment requires an amendment of the ADR.

**Why it matters.** [ADR-0014's amendment of 2026-10-12](../../adr/0014-web-shell.md#amendment-2026-10-12-results-of-the-web-002-validation-gate), design detail 1; [ADR-0002](../../adr/0002-repository-topology-and-contracts.md) decision 6; the [threat model](../../specs/threat-model.md#616-f16-delivering-and-starting-the-web-app), F16.3.

**Known:** only the plan for a single source, in the server's AGENTS.md (the first review's H4, step 2).

**Recommended fix (S).**

1. **bayan-web:** in AGENTS.md and in the header comment of `config/security-headers.ts`, name the server's copy and require a paired bayan-server pull request for every header change; correct the rule for a further Trusted Types policy in both places.
2. **bayan-server:** correct its AGENTS.md.
3. **docs:** compare the two sets in L10's check of the shared files.
4. **At the Phase-0 gate:** write H4's step 2, the web app's build as the single source of its headers, into the WEB-103 and SRV-105 briefs.

### M14. The CRDT import path will meet other people's bytes without automatic fuzzing or full guards

**What we found.**

- **The target is parked.** CORE-010 added the fuzz target `crdt_import`. CI builds it and tests its harness, but the automatic runs leave it out, for the reason that [ADR-0008's note of 2026-11-11](../../adr/0008-crdt-engine-and-local-first.md#note-2026-11-11-the-import-path-is-fuzzed-by-hand-only-while-crdt_import-is-parked) records ([fuzz/ci.py:123](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/fuzz/ci.py#L123-L131)). The monthly dependency session runs it by hand on each new version of Loro ([runbook](../../developer/dependency-update-runbook.md)). A pull request that changes BayanDocs' own checks on imports, `check_header` and `imported_values_too_deep` ([import.rs:146](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/import.rs#L146), [:190](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/import.rs#L190)), gets only the harness's seed tests.
- **It covers one of six ways in.** The target drives only `Doc::import`. `Version::decode`, `VersionVector::decode`, `export_shallow_snapshot`, `export_updates` and `checkout` also take bytes or versions that come from other replicas ([doc.rs:46](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/doc.rs#L46), [:75](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/doc.rs#L75), [:251](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/doc.rs#L251), [:263](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/doc.rs#L263), [:319](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/doc.rs#L319)), without the guard that `import` has (the first review's M2, still open). The harness calls the others only with valid values ([fuzz/src/crdt.rs:688](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/fuzz/src/crdt.rs#L688-L699)), and `VersionVector::decode` not at all. bayan-crdt's own documentation says that every blob from another replica "goes through `Doc::import`" ([lib.rs:19](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-crdt/src/lib.rs#L19)).
- **No fuzzing checks the model any more.** The CORE-004 spike's fuzzer checked that hostile state still normalizes into a valid document ([spikes/crdt-model/src/fuzz.rs:1](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/spikes/crdt-model/src/fuzz.rs#L1)). The fuzz workspace does not depend on bayan-model, so no fuzz target checks that now; bayan-model's own tests still check foreign values written by hand ([foreign.rs](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-model/tests/model/foreign.rs#L7)).
- The fuzz README says that CI runs its targets "every night" ([README.md:3](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/fuzz/README.md#L3)), which does not hold for this one.

**Why it matters.** [ADR-0008](../../adr/0008-crdt-engine-and-local-first.md) decision 4 says that the import path of untrusted updates is fuzzed; [ADR-0025](../../adr/0025-quality-gates.md) decision 4; [AGENTS.md §6](../../AGENTS.md#6-security-and-privacy). Nothing is exposed today, because the engine does not link bayan-crdt; it matters from the first work package that imports other people's changes.

**Known:** partly. ADR-0008's note records the parking, and [CORE-010's brief](../../workpackages/phase-0/CORE-010-fuzz-targets-engine-and-crdt.md) gives the other entry points to CORE-101, but the [CORE-101 draft](../../workpackages/phase-1/core.md#core-101--document-model-v1) does not say so.

**Recommended fix (M, in CORE-101's brief at the Phase-0 gate).**

1. Guard the five other entry points (M2) and extend `crdt_import` to them.
2. Add a target that imports, normalizes and checks the document model's invariants.
3. Say in the brief that, while the target is parked, only its harness's seed tests guard changes to bayan-crdt's import path, and have every such change add seed inputs for the checks it changes, so that those tests reach them.
4. Make "`crdt_import` runs automatically again, or a replacement does" an entry condition of the first work package that imports other people's changes.
5. Correct the two documentation claims.

### L14. Two limits differ from their documentation, or between desktop and web

- **bayan-xml's reservation.** For a UTF-16 part the reader reserves the input's byte count for the decoded text ([source.rs:103](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-xml/src/source.rs#L103)), which can grow to one and a half times that, so the buffer doubles; together with the copy of the current run ([reader.rs:1005](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-xml/src/reader.rs#L1005)), a 256 MiB part can reserve 896 MiB, where the crate documents 768 MiB ([lib.rs:74](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-xml/src/lib.rs#L74)). In WebAssembly, memory grows for what is reserved. This is inferred from the code, not measured, and is recorded only in bayan-core#36's follow-ups.
- **The stack.** The native engine thread has a fixed stack of 2 MiB, so that how deeply an input may nest "does not depend on the machine" ([thread.rs:7](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-engine/src/thread.rs#L7), [:32](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/crates/bayan-engine/src/thread.rs#L32)). In a browser, WebAssembly runs on the JavaScript engine's own stack, which the module cannot set, so the depth at which an input exhausts the stack differs between desktop and web ([ADR-0004](../../adr/0004-fidelity-contract-and-determinism.md); [ADR-0005](../../adr/0005-layout-units-and-deterministic-math.md) decision 5), and the engine's fuzz targets, which call the engine directly, test neither. **Known:** the merge of [bayan-core#39](https://github.com/BayanDocs/bayan-core/pull/39) kept this as a follow-up and decided that parser depth limits measured in WebAssembly are the fix; no work package has taken it yet.

**Fix (S):** reserve exactly (count first, then allocate) and measure it in the memory tests; give the parsers explicit depth limits that fit the smaller stack, as bayan-core#39 decided, tested at the maximum depth both natively and in WebAssembly.

## What is in good shape

- **Layering and memory safety.** No product crate depends on the lab or a spike, and every dependency points to the same layer or below; bayan-opc now uses bayan-xml, in the same layer. `unsafe` code exists only in bayan-ffi, every block with a `// SAFETY:` comment, and lints enforce both. The C header matches spec §3.1, and the engine's WebAssembly module imports only three functions of wasm-bindgen's glue, which `cargo xtask wasm-package` checks in the artifacts workflow.
- **Determinism.** The product crates have no hash maps, clocks or environment reads, apart from the bindings' monotonic clock for recordings, which spec §10 allows, and start no thread but the engine's own, whose stack has a fixed size. The gate now checks the source of the code that ships for ways out to the outside world, as far as a model of the source text can (bayan-core's [AGENTS.md:61](https://github.com/BayanDocs/bayan-core/blob/3423a4f60ba3a8896dc944f457fa796bf1a5146a/AGENTS.md#L61)), and what the compiler read. The lab's metrics are computed in integers.
- **Fuzzing.** Eighteen targets are built in CI and seventeen run automatically. The engine's harness checks every answer against the schema and fails on a panic even when the engine catches it, and the fuzz workspace's lockfile agrees with the main one.
- **The Fidelity Lab.** The PDF extractor refuses rather than repairs, limits every byte, count, depth and operator, tests each limit, never quotes a document in an error, and is fuzzed. Private documents are never named, and the HTML report loads nothing from elsewhere.
- **The shells.**
  - Both follow spec §12.1, with tests against the real engine, and show users no error text from the engine.
  - The desktop's sanitizer job runs the real engine, and its copies of the C header and schema are byte-identical to bayan-core's.
  - axe runs on every state of the web app in three browsers and both themes, under the production CSP and Trusted Types; its two packages are MPL-2.0, run no install scripts and were more than 24 hours old when pinned.
  - Both shells pin bayan-core as [ADR-0017's amendment of 2026-10-12](../../adr/0017-supply-chain-and-dependency-policy.md#amendment-2026-10-12-the-bayan-core-commit-that-a-shell-builds-from) requires.
  - X-005's first part installs Ubuntu packages from a lock taken from the index that apt verified, on a base image pinned by digest.
  - Neither shell logs content, the web app still has exactly one Trusted Types policy, and nothing fetches remote resources.
- **The server.** Its headers equal bayan-web's; logging stays content-free and drops peer addresses; the two databases' migrations are compared in CI; the MLS spike's browser tools are pinned with SHA-256 hashes and never reach the image; and the time-limited advisory exception was removed as planned.
- **CI and the supply chain.**
  - All 41 workflows have `permissions: {}` at the top, a timeout on every job and `persist-credentials: false` on every checkout, with no `pull_request_target`, no `workflow_run`, no event data in scripts and no secrets.
  - They use only GitHub's own actions, pinned to full SHAs at the same versions everywhere, and check every download and every image against hashes written in the repository, except Qt's archives (L9).
  - zizmor 1.32.0 reports nothing in any repository.
  - X-004 is complete: write permissions exist only in the upload jobs of CodeQL and Scorecard and in this repository's website deployment.
  - Every required check runs on pull requests and in the merge queue.
  - The 19 shared files are byte-identical in all five repositories, and the shared supply-chain checker in the two that have it.
