## Summary for the owner

The foundations are in good shape where it matters most. The crates of bayan-core respect their layers, and nothing in the product depends on a spike. Unsafe Rust exists only in the C binding, where every block is justified. The determinism rules (integer layout units, no hash-map order, no platform math) are followed and enforced by lints. Neither app lays out, measures or hit-tests text itself; both leave that to the engine. The server never sees or logs document content. All 38 CI workflows in the five repositories follow the security conventions, and the files that must be identical in every repository are identical. The section [What is in good shape](#what-is-in-good-shape) lists more.

The problems sit at the edges between the pieces and in the safety nets. Seven are rated high:

1. **Some safety nets exist only on paper.** GitHub's branch rules do not yet require the workflow lint or the CodeQL scans that the settings baseline lists (H1). The engine's artifact tests can fail without blocking a merge: they are the only run of Miri, the checker for unsafe code, and the only tests of the web worker host (H1). Fuzzing, which throws millions of malformed inputs at a parser to find crashes, never runs automatically (H2).
2. **Two parsers can be pushed far past their memory limits.** A crafted 4 MB legacy Office file can make the engine run out of memory and stop (H3), and the XML reader can use several times its documented maximum (M3). No parser can be stopped or held to a time limit yet, which ADR-0006 requires (H6). Nothing reaches these parsers from a user's document today, so this is the right moment to fix them.
3. **The contract between the engine and the two apps is incomplete.** Each app has filled the holes in its own way, and the two already behave differently for keys, shortcuts and crash recovery (H5, M6). One hole will make the desktop app show outdated page images once the engine lays out pages in the background (H5).
4. **The server's copy of the web app's security headers is weaker than the web app's own** (H4). On the deployment the ADRs make the default, it drops the rule that only one Trusted Types policy may exist.
5. **Several things the ADRs require of Phase 1 are missing from the Phase-1 drafts** (H7, M1). These are the core MLS crate that the server's validator must come from, the conditions you set when you kept Loro, and the protocol additions the app spikes asked for. The Phase-0 gate is the place to add them.

Four items are yours alone:

- run the GitHub settings audit and apply it (H1, issue [#15](https://github.com/BayanDocs/docs/issues/15));
- confirm that Loro's crash reports went out (M12);
- decide the licence of the shared supply-chain checker (L2);
- schedule the deferred screen-reader and input-method tests before the accessibility work packages start (M9).

Everything else is work for agent sessions, mostly small.

## How to read this report

- **Severity.** *High*: breaks an Accepted ADR or a spec, or is a security weakness with a realistic path, and will spread into Phase-1 work if not fixed now. *Medium*: drift or a gap with limited reach, or missing tests for important behaviour. *Low*: hygiene and documentation drift. Nothing found is exploitable through a released product today, because nothing has been released and no user document reaches the parsers yet, so no finding is rated critical.
- **Size.** *S*: one small pull request, under a day. *M*: a few days, one work package. *L*: several work packages.
- **Known.** Whether the problem was already recorded somewhere (an ADR, a report, a code comment). A known problem is listed when no work package or follow-up owns it yet.

## High

### H1. The merge gates do not enforce what the ADRs and the settings baseline require

**What we found.**

- **The live rules lag the baseline.** A ruleset is GitHub's protection of a branch; its *required checks* are the CI jobs that must pass before anything can be merged. The ruleset that protects `main` in this repository was created on 2026-10-06 and last changed on 2026-10-09 (read from GitHub's public API on 2026-10-27). It requires five checks: `scripts/verify.sh`, `DCO`, `REUSE lint`, `No update bots` and `pip-audit`. The settings baseline, [scripts/github-settings.py](../../scripts/github-settings.py), also lists `Workflow lint`, `CodeQL (actions)`, `CodeQL (python)` and `CodeQL (javascript-typescript)`. X-002 added those on 2026-10-10, and they were never applied. The code repositories' rulesets cannot be read from a review session; they were probably applied at the same time and lag in the same way.
- **The baseline leaves out the artifact tests.** bayan-core's [`artifacts.yml`](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/.github/workflows/artifacts.yml#L14-L18) runs on every pull request, but none of its jobs is required, and it does not run in the merge queue (no `merge_group` trigger). Its jobs are the only CI run of three things. The first is bayan-ffi's tests under Miri, an interpreter that detects undefined behaviour in `unsafe` code ([`Miri (bayan-ffi)`](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/.github/workflows/artifacts.yml#L322)). The second is the tests of the worker host `bayan-worker.js`, the web boundary that receives the page's messages, together with the check that engine panics print nothing. The third is the check that every platform renders the same tile ([`Same tile everywhere`](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/.github/workflows/artifacts.yml#L275)). Each can fail without blocking a merge; `cargo xtask verify` runs none of them.
- **The owner's records disagree with GitHub.** Issue [#15](https://github.com/BayanDocs/docs/issues/15) ("Apply the GitHub settings baseline …") is open and items 3 to 6a of the [owner checklist](../09-owner-checklist.md) are unticked, although rulesets exist.

**Why it matters.** [AGENTS.md §4](../../AGENTS.md#4-the-verification-gate-is-sacred) says the workflow lint and CodeQL "must pass". [ADR-0006](../../adr/0006-rust-core-and-memory-safety.md) decision 2 requires Miri coverage of `unsafe` code. The [threat model](../../specs/threat-model.md#11-principal-threats) counts T4 (hostile messages at the boundary) as in place, and T20 counts the engine's silence as tested. From today the orchestrator merges approved work without the owner. Its procedure checks every check, not only the required ones ([plan/12 §5](../12-orchestration.md#5-merge-with-the-owners-sign-off)). The ruleset is the backstop when a result is missed, and GitHub lost two job results on [docs#49](https://github.com/BayanDocs/docs/pull/49) that same day.

**Known:** no.

**Recommended fix (S).**

1. **Owner:** run `python3 scripts/github-settings.py audit`, then `apply`, for all five repositories, as [developer/github-settings.md](../../developer/github-settings.md) describes. Then tick checklist items 3 to 6a and update or close issue #15.
2. **A docs pull request:** add `Same tile everywhere` and `Miri (bayan-ffi)` to bayan-core's required checks in the baseline. `Same tile everywhere` already fails when any driver job failed or was skipped. The owner then applies the change.
3. **A bayan-core pull request:** add `merge_group: types: [checks_requested]` to `artifacts.yml`. The alternative is to move the Node.js driver and Miri into `cargo xtask verify`.

### H2. Fuzzing never runs in CI, and four kinds of untrusted input have no fuzz target

**What we found.**

*Fuzzing* feeds a parser millions of random and mutated inputs to find crashes and hangs. bayan-core has eight fuzz targets, all for bayan-opc and bayan-xml ([`fuzz/Cargo.toml`](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/fuzz/Cargo.toml)). It runs them only by hand, in the session that changes a parser, which records in its pull request how long they ran ([fuzz/README.md](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/fuzz/README.md#L18-L34)). No workflow in any repository builds or runs them, so a change to a parser's interface can even break its target unnoticed.

Four kinds of input that come from outside have no target at all:

- **Engine protocol messages, tile requests and the configuration.** The engine's hostile-input test calls itself "a deterministic, bounded stand-in for fuzzing until the fuzzing workspace exists" ([hostile_input.rs:3](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-engine/tests/engine/hostile_input.rs#L3)), and that workspace exists now.
- **Recordings that `diag.replay` reads**, which the spec treats as untrusted ([§10](../../specs/engine-protocol.md#10-record-and-replay)).
- **CRDT updates from other people.** The only fuzzer for them is the CORE-004 spike's own mutator, written before the owner accepted libFuzzer's licence ([fuzz.rs:3](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/spikes/crdt-model/src/fuzz.rs#L3)).
- **The Fidelity Lab's own ZIP, package and XML readers** (M4).

The fuzz README's first line says protocol messages have a target. They do not.

**Why it matters.**

- [ADR-0025](../../adr/0025-quality-gates.md) decision 4: "short fuzz runs on every pull request touching it, continuous fuzzing on a schedule".
- [ADR-0008](../../adr/0008-crdt-engine-and-local-first.md) decision 4: the CRDT import path "is fuzzed".
- [plan/07 §2](../07-quality-security-testing.md#2-ci-gates-per-repository) names "fuzz smoke runs" in bayan-core's pull-request gate and "long fuzzing" nightly. Its testing table lists engine protocol messages among the parsers to fuzz.
- Phase 1 adds about a dozen parsers (CORE-102 to CORE-106, CORE-110, CORE-122, CORE-123). CORE-102's exit evidence already asks for a "fuzz target running in CI", but no work package builds the CI job.
- H3 shows what a parser can still hide after CORE-005's 5.97 CPU-hours of fuzzing by hand.

**Known:** partly. [ADR-0017's amendment of 2026-10-08](../../adr/0017-supply-chain-and-dependency-policy.md#amendment-2026-10-08-the-libfuzzer-license-for-fuzzing) calls CI fuzzing "a follow-up"; nothing schedules it.

**Recommended fix (M, one bayan-core work package).**

1. **A `fuzz.yml` workflow.** It builds every target with the pinned nightly toolchain and cargo-fuzz 0.13.2, checked against a pinned SHA-256. On every pull request and in the merge queue, it runs each target for a minute or two from seed corpora committed under `fuzz/corpus/` and made from the existing test fixtures. Every night, it runs each target for longer. Use GitHub's own runners: ClusterFuzzLite, which plan/07 mentions, would need the owner's approval as a third-party action.
2. **Crash inputs stay private.** A crash is handled as a security report ([SECURITY.md](../../SECURITY.md)), not uploaded as a public workflow artifact.
3. **New targets:** engine message handling after a handshake, `diag.replay`, `bayan_render_tile`'s request and the configuration, and a `crdt_import` target that reuses the spike's mutations.
4. **Clean-up:** correct the README's first line, and make the pull-request job required once it is stable (H1).

### H3. A crafted compound file makes bayan-opc use about a thousand times its size in memory

**What we found.** *OLE compound files* (Microsoft's Compound File Binary format) contain three things BayanDocs will open: legacy `.doc` files, the VBA projects inside `.docm` files, and password-encrypted documents.

- **Nothing limits cfb's own work.** [`CompoundFile::open`](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-opc/src/compound_file.rs#L95-L96) hands the whole input to the cfb crate before any of bayan-opc's limits apply.
- **The cfb case.** A crafted compound file makes cfb 0.15.0 allocate about a thousand times its size before it refuses the file as malformed. Reproduced in this review on the reviewed commit, in a release build, a 266 KB file reached a peak of 265 MB and a 1 MB file 1.05 GB, taking 3 s. A 4 MiB file asks for 4 GiB. An allocation failure that large ends the process with an abort, which neither the C interface nor the WebAssembly worker can catch. The case affects every program that reads compound files with cfb 0.15.0, so how such a file is built is withheld until the owner has reported it privately to cfb's maintainer; the brief of the follow-up that fixes it will carry the details.
- **The nesting case.** Separately, opening keeps the full path of every entry, twice ([compound_file.rs:113](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-opc/src/compound_file.rs#L113), [:127](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-opc/src/compound_file.rs#L127)). Storages nested inside each other therefore cost memory and time that grow with the square of their depth. 2,000 nested storages in a 266 KB file took 229 MB and were accepted, well within the default limit of 65,536 entries.
- **Promise and tests.** The crate documents a limit for compound files ([lib.rs:59](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-opc/src/lib.rs#L59)) that bounds neither case, and neither file is in its tests or fuzz corpus.

**Why it matters.** [ADR-0006](../../adr/0006-rust-core-and-memory-safety.md) decision 5 says every parser enforces limits on size, depth and count. The [threat model](../../specs/threat-model.md#11-principal-threats) counts T1 and T3 as "in place for bayan-opc". Nothing reaches this code today, but it is the planned entry point for `.doc` import, VBA projects and encrypted packages.

**Known:** no. The owner's acceptance of cfb on 2026-10-10 concerned only the `unsafe` code of its uuid dependency.

**Recommended fix (S–M, bayan-core).**

1. Check the header and the DIFAT chain before calling cfb, so that what cfb allocates is bounded by the file's size; the follow-up's brief gives the details.
2. Add a size limit and a depth limit for compound files to `Limits`.
3. Keep each entry's parent and name instead of its full path.
4. Add both crafted files as regression tests and as fuzz seeds; the cfb one only once the owner says the upstream report allows it to be published.
5. **Owner:** report the cfb case privately to cfb's maintainer, as the owner did for Loro's findings; the orchestrator holds the reproduction.

### H4. The server serves the web app with a weaker copy of its security headers

**What we found.**

The browser enforces a page's protection through HTTP headers, chiefly the Content Security Policy (CSP), which says what the page may load and run. Its Trusted Types rules allow script addresses only through named, reviewed policies. The web app's headers exist in three places:

- **bayan-web** defines them in [`config/security-headers.ts`](https://github.com/BayanDocs/bayan-web/blob/01c59788fa755eea8665332d88b18174a90e1a22/config/security-headers.ts#L19-L28) and repeats them in [`deploy/nginx/security-headers.conf`](https://github.com/BayanDocs/bayan-web/blob/01c59788fa755eea8665332d88b18174a90e1a22/deploy/nginx/security-headers.conf#L3). A unit test keeps those two equal.
- **bayan-server** serves the built web app from `BAYAN_WEB_DIR` ([http/mod.rs:45](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/crates/bayan-server/src/http/mod.rs#L45)), as [ADR-0015](../../adr/0015-server-architecture.md) decision 2 makes the default deployment. It has a third copy ([headers.rs:11](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/crates/bayan-server/src/http/headers.rs#L11)), written in SRV-001 on 2026-10-05 and never changed since. It was never in step: WEB-001 already had stricter values the day before.

The server's CSP has no `trusted-types` directive and no `frame-src 'none'`, and it has `form-action 'self'` instead of `'none'`. Its Permissions-Policy differs too. Without a `trusted-types` directive, browsers let the page's scripts create any number of Trusted Types policies, including a permissive `default` policy. The server's test compares its responses with the server's own constant ([tests/http.rs:14](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/crates/bayan-server/tests/http.rs#L14)), so no test can see the drift.

The way the app is deployed is unsettled as well:

- WEB-103 plans a container image of its own, and a public demo on GitHub Pages, which cannot send custom headers at all: no `Integrity-Policy`, no `frame-ancestors` and no cross-origin isolation.
- The server's [README](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/README.md#L5) says that `docker run` gives a complete deployment. The image contains no web app, though: operators mount a build themselves, and no work package puts it in the image.

**Why it matters.**

- [ADR-0014's amendment of 2026-10-12](../../adr/0014-web-shell.md#amendment-2026-10-12-results-of-the-web-002-validation-gate), design detail 1: the CSP "is WEB-001's with one change: `trusted-types bayan-script-url`", and "any further policy needs an amendment of this ADR".
- [ADR-0002](../../adr/0002-repository-topology-and-contracts.md) decision 6: no duplication across repositories.
- [Threat model](../../specs/threat-model.md#616-f16-delivering-and-starting-the-web-app) F16.3. The one-policy rule is part of what keeps an injected script away from the keys the web app will hold (T11).

**Known:** no. The threat model's endpoint requirements assume the server sends ADR-0014's headers.

**Recommended fix.**

1. **Now (S, bayan-server):** make the server's headers equal to bayan-web's current set, and test them against values copied from a named bayan-web commit.
2. **Next (M, WEB-103 with SRV-105 or X-101):** make the web app's build the single source. The build writes its headers and cache rules into the built app, and the server applies exactly those to the files under `BAYAN_WEB_DIR` and refuses to start without them. The nginx file is generated from the same source.
3. **Deployment decisions:** settle which deployments exist and put the web app into the server's image, or correct the README. Either drop the GitHub Pages demo or record it in an ADR-0014 amendment as a demo without enforced integrity.

### H5. The engine protocol leaves behaviour to the shells, and they already decide differently

The two shell spikes listed what engine protocol v0 lacks: [ADR-0013's validation result](../../adr/0013-desktop-shell.md#validation-result-desk-002-2026-10-12), the DESK-002 report and [ADR-0014's amendment](../../adr/0014-web-shell.md#amendment-2026-10-12-results-of-the-web-002-validation-gate). - moving the caret to an offset;

- clipboard bytes;
- invalidation narrower than every page on `view.set`;
- the worker host accepting the engine module's hash ([bayan-web issue 8](https://github.com/BayanDocs/bayan-web/issues/8)), which [threat model §13.3](../../specs/threat-model.md#133-later-phases-and-other-repositories) item 4 requires before collaboration runs in browsers.

This review adds one more. Accessibility nodes carry no language or direction, and the web mirror marks the whole document as English, left to right ([index.html:2](https://github.com/BayanDocs/bayan-web/blob/01c59788fa755eea8665332d88b18174a90e1a22/index.html#L2)). - The protocol's first goal: "One contract for both shells, so behavior cannot drift" ([spec §1](../../specs/engine-protocol.md#1-goals)).
- [ADR-0002](../../adr/0002-repository-topology-and-contracts.md) decisions 2 (contract-first) and 6.
- [plan/03 §3](../03-architecture.md#3-repositories-and-their-boundaries): "If two shells would need the same logic, it belongs in core".
- DESK-101 and WEB-101 will build navigation, find and copy on exactly these paths.

**Known:** each gap is in a spike report. The divergence between the shells, the reach of the tile-freshness assumption (invalidations that no request caused) and the missing language are not recorded, and no brief carries any of it.

**Recommended fix.**

**M:** one contract-first pull request to [specs/engine-protocol.md](../../specs/engine-protocol.md), from a planning session before the Phase-0 gate refines CORE-125, DESK-101 and WEB-101. It should cover:

- a render revision on `render.invalidate` and on every tile (or tiles delivered in order with events, as on the web);
- which key presses a shell forwards (proposal: all, with the shell deciding only which to keep from the browser or the operating system), with the manifest's shortcuts as structured bindings per platform;
- `hello.shell.platform` naming the operating system;
- `input.text` with a range to replace;
- a hit-test query and a message that moves the caret;
- selection, line ranges, language and direction in accessibility nodes;

- the module hash in the worker host's `init`.

Then add these to CORE-125's scope.

**S, now:** the desktop drops its Ctrl+=, Ctrl+− and Ctrl+0 bindings and forwards PageUp, PageDown, Home and End as the web does.

### H6. No parser can be stopped or held to a time budget

**What we found.**

- **The rule.** [ADR-0006](../../adr/0006-rust-core-and-memory-safety.md) decision 5 requires every parser and layout pass to enforce limits "on size, depth, count and time", and to be "cancellable". [plan/03 §12](../03-architecture.md#12-cross-cutting-rules) repeats it.
- **No time limit or cancellation in the parsers.** bayan-opc and bayan-xml limit sizes, depths and counts, but neither has a time or work budget, nor any way to stop. Opening a package, reading a ZIP archive, writing a package (which decompresses every part to check it), opening a compound file and canonicalizing XML always run to the end. H3 showed a 3-second run that nothing could interrupt.
- **No way to ask the engine to stop.** The C interface has no such function and the protocol no such message. On the web, the main thread can only terminate the whole worker.
- **A time limit has to be counted work.** The engine may not read a clock ([ADR-0012](../../adr/0012-engine-boundary.md) decision 5), so a time limit has to be a deterministic budget of counted work.

**Why it matters.** It is a rule of an Accepted ADR. The Phase-1 importers (CORE-102 to CORE-107) and layout (CORE-113) will be built on these function signatures. Background layout ([plan/03 §6.1](../03-architecture.md#61-opening-a-docx)) needs cancellation to stay responsive.

**Known:** no.

**Recommended fix (M).**

1. **Decide first**, in an ADR-0006 amendment from a planning session, before CORE-102 is refined:
   - a work budget counted in units of work (bytes decoded, events, nodes), which callers pass in;
   - a cancellation flag that the host can set between messages: on desktop, for example, a tenth C function; on the web, a shared flag, which the web app's cross-origin isolation already allows, or a documented restart of the worker;
   - where the budget and the flag are checked;
   - one `Limits` value that configures both crates.
2. **Then a bayan-core work package** adds the budget and the flag to bayan-opc and bayan-xml.

### H7. Phase-1 server work cannot take MLS and protocol code from bayan-core, as the ADRs require

**What we found.**

- **Where the ADRs put this code.** [ADR-0016](../../adr/0016-e2ee-and-identity.md) decision 1 puts MLS in a core crate, `bayan-mls`, "shared with the server for validation". [ADR-0002](../../adr/0002-repository-topology-and-contracts.md) decisions 4 and 6 have the server consume core crates as Git dependencies pinned to a tag and commit, so that logic needed by both is written once.
- **Where the Phase-1 drafts put it.** No Phase-1 work package creates `bayan-mls`. SRV-103 builds "public-state validation of commits and role enforcement" in the server, and SRV-104 creates bayan-core's `bayan-protocol` crate, "used by both core and server" ([server drafts](../../workpackages/phase-1/server.md)).
- **The server cannot depend on bayan-core today.**
  - `deny.toml` allows no Git source ([deny.toml:69](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/deny.toml#L69)).
  - The lockfile check refuses every package from a Git repository ([lockfile_age.rs:257](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/xtask/src/supply_chain/lockfile_age.rs#L257)).
  - bayan-core has no tags.
  - [ADR-0017's amendment of 2026-10-12](../../adr/0017-supply-chain-and-dependency-policy.md#amendment-2026-10-12-the-bayan-core-commit-that-a-shell-builds-from) says the server's Git dependencies on core need "a decision of its own".
- **The SRV-002 spike's validator is not a starting point as it stands.** It lives in bayan-server, under the AGPL, and:
  - accepts every ciphersuite the build knows, the provisional post-quantum one included ([validator.rs:106](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/spikes/mls/bayan-mls-spike/src/validator.rs#L106));
  - refuses the external commits that [ADR-0029](../../adr/0029-identity-devices-and-recovery.md) now needs for resyncs and recovery joins;
  - takes randomness and time from the platform ([threat model §13.3](../../specs/threat-model.md#133-later-phases-and-other-repositories) item 2);
  - uses a RustCrypto provider that brings `crypto-bigint` 0.5.5, with the timing advisory RUSTSEC-2026-0387. bayan-server's `deny.toml` excepts that advisory only because the spike is never built into the server ([deny.toml:15](https://github.com/BayanDocs/bayan-server/blob/3d6e9ea3569a6f64f0eb30e9c4dee053e57075c2/deny.toml#L15)).

**Why it matters.** Without a decision, the role policy and the commit validator get written in bayan-server in Phase 1, and again in `bayan-mls` in Phase 3. That is the duplication ADR-0002 forbids, and in the security-critical code of the project.

**Known:** partly. bayan-server's AGENTS.md says that "the work package that needs a Git dependency teaches it first", and the threat model §13.3 lists the spike's platform calls. The missing core work package and the `crypto-bigint` conflict are not recorded.

**Recommended fix (L, at the Phase-0 gate).**

1. **A core work package for `bayan-mls` v0**, ahead of SRV-103: the role policy, commit and key-package validation, the commit types of ADR-0029 and ADR-0030, randomness and time from the host, and no provisional suites by default. The alternative is an explicit decision that SRV-103 builds against a stand-in for it.
2. **A decision on how the server pins core commits.** Keeping the 24-hour minimum, as bayan-web does for its engine pin, needs no relaxation of ADR-0017. It needs a change to `check-lockfile-age` in both repositories that accepts Git packages only from BayanDocs/bayan-core, at a commit on `main` that is at least 24 hours old.
3. **A note in the `bayan-mls` brief** that its provider must not need `crypto-bigint` 0.5, or that the work waits for `elliptic-curve` 0.14.
4. **A "constraints changed since the spike" section in the spike's report**, `spikes/mls/REPORT.md` in bayan-server.

### M2. The CRDT adapter does not guard every path that untrusted bytes take

**What we found.**

- **Unguarded entry points.** `import` contains Loro's panics and poisons the document ([doc.rs:277](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/doc.rs#L277)). Three other entry points pass bytes from other replicas to Loro without that guard: `VersionVector::decode` ([doc.rs:75](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/doc.rs#L75)), `export_updates` ([:263](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/doc.rs#L263)) and `checkout` ([:312](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/doc.rs#L312)).
- **No preset for another member's snapshot.** The import presets cover an update (no snapshots) and a snapshot this device wrote itself (values not inspected) ([import.rs:38](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/import.rs#L38), [:47](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/import.rs#L47)). None fits a snapshot made by another member, which the threat model's flow F8 imports.
- **Fail-open counting.** The check for deeply nested values passes every kind of operation it does not list ([import.rs:221](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/import.rs#L221)), and an inconsistent span counts as zero operations ([:172](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-crdt/src/import.rs#L172-L173)).
- **Peer IDs are not tied to the sender.** `import` does not know who sent a blob, and nothing ties a change's Loro peer identifier to the authenticated MLS sender. A collaborator who may edit could therefore write changes under another member's peer identifier. Loro identifies changes by peer and counter, so a forged change that takes another member's next counter could make replicas discard that member's real change as a duplicate: a silent, permanent divergence. This is inferred from Loro's design; it was not reproduced in this review.

**Why it matters.**

- [ADR-0008](../../adr/0008-crdt-engine-and-local-first.md) decision 4.
- [AGENTS.md §6](../../AGENTS.md#6-security-and-privacy): every network message is hostile.
- The threat model's T7 and F6.10 take the author of a change to be the sender whose MLS signature it carries.

**Known:** partly. The CORE-004 report §8.3 covers pending changes and the cost of overlapping marks.

**Recommended fix.**

**S, in CORE-101:**

- one guard for every entry point that takes bytes from others;
- an import preset for others' snapshots, with value inspection;
- an exhaustive, fail-closed value check with a test for each kind;
- refusing inconsistent spans.

**A decision, in an ADR-0016 or ADR-0008 amendment or in SRV-104's sync protocol:** bind each device's peer identifier to its identity, and refuse imported changes whose peers are not the sender's. Snapshots from editors remain an accepted residual risk.

### M3. bayan-xml exceeds its documented memory bound on two crafted inputs

**What we found.** Two inputs keep far more memory than the input itself:

- **The XML declaration.** The reader collects every field of the declaration before checking it ([source.rs:144](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-xml/src/source.rs#L144)), empty names included. Each 4 bytes of input keep about 40 bytes.
- **Runs of text.** A run of text keeps an entry for every piece ([reader.rs:941](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-xml/src/reader.rs#L941)), and `&lt;` is a new piece every 4 bytes.

Reproduced in this review with 32 MiB parts, against 0.1 MB for plain text:

- a long declaration added 328 MB, 10 times the input, before it was refused;
- a run of `&lt;` added 205 MB, 6.4 times the input.

At the 256 MiB part limit that is about 2.6 GiB and 1.6 GiB. The crate documents 768 MiB as its worst case ([lib.rs:74](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-xml/src/lib.rs#L74)). bayan-opc's 100:1 limit on the compression ratio lets such a part travel in a `.docx` of a few megabytes, and the web engine has at most 4 GB of memory ([ADR-0014](../../adr/0014-web-shell.md) decision 8).

**Why it matters.** [ADR-0006](../../adr/0006-rust-core-and-memory-safety.md) decision 5, and the crate's own documented bound, which the `stays_linear_*` tests do not check because they measure time only.

**Known:** no.

**Recommended fix (S, bayan-core).**

1. Refuse a fourth declaration field as soon as it is read.
2. Decode runs of references as they are read.
3. Add regression tests that measure peak memory in a child process.

### M5. The outside-world rule is enforced only by review, and the engine already reads the environment

**What we found.**

- **One environment read today.** The engine starts its thread without a stack size ([thread.rs:166](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/crates/bayan-engine/src/thread.rs#L166)). Rust's standard library then takes the size from the `RUST_MIN_STACK` environment variable. The depth at which a deeply nested input overflows the stack therefore depends on the environment; CORE-004 measured its stack-overflow finding at the 2 MiB default.
- **What the lints cover.** `clippy.toml` forbids only floating-point methods and hash collections ([clippy.toml:9](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/clippy.toml#L9), [:81](https://github.com/BayanDocs/bayan-core/blob/bc903b233e4eabf4bdc2acc77fca607985de9eef/clippy.toml#L81)). Nothing rejects clocks, environment variables, files, sockets or processes in the engine's crates, and nothing checks what the engine's WebAssembly module imports from its host.
- **Platform calls arriving through dependencies:**
  - cfb brings `web-time`, a clock, on wasm32;
  - Loro's randomness and clock are an accepted exception;
  - OpenMLS reads the clock and the platform's randomness ([threat model §13.3](../../specs/threat-model.md#133-later-phases-and-other-repositories) item 2).
- **The planned check comes late.** ADR-0012's amendment asks for a check of the imports only when `bayan-crdt` is first linked.

**Why it matters.** [ADR-0012](../../adr/0012-engine-boundary.md) decision 5. [ADR-0005](../../adr/0005-layout-units-and-deterministic-math.md) decision 5: no clock, locale, environment or thread scheduling in output. [plan/03 §12](../03-architecture.md#12-cross-cutting-rules): the engine "reads no environment variables".

**Known:** the import check is planned for later; the rest is not recorded.

**Recommended fix (S, bayan-core).**

1. Give the engine's thread an explicit stack size.

### M6. Neither shell recovers from an engine panic as the protocol says

**What we found.**

- **bayan-desktop** ends the session for good after an unrecoverable `engine.error` ([documentsession.cpp:147](https://github.com/BayanDocs/bayan-desktop/blob/b9b217a3ab7df2b217303f0915c9eacc35a54f74/src/app/documentsession.cpp#L147)).

**Recommended fix (S, in both shells, and one sentence in spec §12).**

## What is in good shape

- **Layering.** bayan-units, bayan-opc and bayan-xml depend only on third-party crates. bayan-model depends on bayan-crdt, in the same layer. bayan-engine depends only on serde, serde_json and schemars, and the binding crates only on the engine. No product crate depends on a spike or on the Fidelity Lab, and the lab is not in any shipped artifact.
- **Memory safety.** `#![forbid(unsafe_code)]` holds in every crate except bayan-ffi and bayan-wasm. In bayan-ffi every `unsafe` block is marked with `#[expect(unsafe_code, reason = …)]`, and each has a `// SAFETY:` comment that holds. Every C entry point catches panics, and the panic hook keeps engine panics silent.
- **Determinism.** Output code has no hash maps and no platform floating-point math; both bans are lints at the `forbid` level, proven by a lint canary. bayan-units' functions are tested natively and in WebAssembly against independent references. Loro's maps and mark sets leave the adapter sorted, its undo clock is neutralized, and the host's peer identifier replaces Loro's random one.
- **Engine protocol v0.** The engine implements its spec closely:
  - the handshake;
  - envelopes that refuse duplicate keys;
  - every limit of §13, on outgoing messages too;
  - error arguments without content;
  - recordings that the engine never writes to disk, replayed with the replaying engine's own configuration.
- **Parsers.** The ZIP reader:
  - checks entry counts before allocating;
  - refuses path traversal, names that differ only by case or encoding, overlapping entries, encrypted entries and links;
  - limits the compression ratio.

  Both XML parsers refuse document type declarations and every entity but the five predefined ones, and check depth, attributes and names before doing the work. No parser error carries document text.
- **Shells.** Neither shell hit-tests, moves a caret or selection, or measures text. Qt never decodes document data. The web app:
  - builds no HTML from strings;
  - has exactly one Trusted Types policy, created in one module;
  - sends a strict CSP and enforces Subresource Integrity with a build that fails closed;
  - checks the engine's files before starting the worker (with the gap of H5);
  - compiles against the generated protocol types.

  Neither shell logs content.
- **Server.** The server is content-blind:
  - no route reads a request body, and peer addresses are discarded;
  - request IDs reveal nothing, and logging is content-free and tested at the most verbose level;
  - configuration refuses unknown keys, takes secrets from files and redacts them;
  - the header-read timeout and graceful shutdown are tested;
  - the container is built from scratch, runs as non-root on a read-only root, and allows only listed files;
  - queries are static and compile-checked, and SQLite is the only native code.
- **Supply chain and CI.** All 38 workflows in the five repositories follow the workflow conventions:
  - minimal permissions;
  - no persisted credentials;
  - GitHub's own actions pinned to full SHAs;
  - timeouts and concurrency groups;
  - no `pull_request_target`;
  - no event data in scripts;
  - `merge_group` on required workflows.

  The shared files are byte-identical everywhere. Exact pins, committed lockfiles, the age checks, cargo-deny, pnpm's audit and the lockfile-integrity check are in place. Every committed test document and font has a recorded licence.
- **Fidelity Lab.** The lab calls `curl` without a shell, allows only HTTPS (plain HTTP only to the local machine, for tests), never relaxes certificate checks, follows no redirects, and passes credentials on standard input.
