# ADR-0029: Identity keys, device approval and account recovery

- **Status:** Proposed (SRV-003, 2026-10-14). Not binding until the owner accepts it; an expert review of its constructions is recommended before the Phase-3 work package that builds them, and the external audit before collaboration leaves beta covers it (SEC-08).
- **Date:** 2026-10-14
- **Deciders:** proposed by the SRV-003 implementer session; the owner decides (ADR-0001 Decision 5: it changes a security design)
- **Related:** COL-05, COL-06, COL-13, SEC-08, SEC-11, SEC-13, OPS-09, [ADR-0015](0015-server-architecture.md), [ADR-0016](0016-e2ee-and-identity.md), [ADR-0028](0028-server-tls.md), [ADR-0030](0030-commit-acceptance-and-group-repair.md), [threat model v1](../specs/threat-model.md) (§5, flows F3, F9, F10, F11; threats T23, T24, T27–T30, T39), SRV-002, SRV-003, SRV-101, SRV-103

## Context

ADR-0016 decides the principles of identity and recovery: each user has a long-term identity key that cross-signs device keys, MLS credentials bind device signature keys to the user's identity and clients verify the chain, users can compare safety numbers or QR codes, key transparency comes later, the server cannot silently add devices to a user (Decision 6), a recovery kit is always available and passkey PRF unlock is an optional convenience, never the only path (Decision 7). The MLS spike SRV-002 named devices with plain `user/device` credentials and left cross-signing to SRV-003 ("designed in SRV-003, built in Phase 3").

The threat model v1 analyses device enrollment, recovery and device loss, and finds four problems that the principles alone leave open:

1. **No way back into one's documents.** The role policy of ADR-0016's amendment of 2026-10-07 (design detail 3) and the SRV-002 validator accept commits only from members, and a regular MLS commit cannot remove its own committer (RFC 9420 §12.2). A user who loses every device therefore has no device left in any group: only owners can add the user's new device, and if the user was a document's only owner, nobody can. Worse, that document's membership can never change again, because every commit must leave each user who has a device in the group a role and at least one owner, so the lost owner's devices can never be removed. A recovery kit that brings back the identity key but not the documents falls short of Decision 7.
2. **Documents only the user held have no other copy.** MLS's forward secrecy means a new device cannot read earlier epochs, and in a document that only the user's own devices belong to, nobody else can send the new device a snapshot.
3. **Approving a device must authenticate it.** If an approving device sees only "a device is waiting for approval", the server can register a device of its own at the same moment and have the user approve it.
4. **First contact trusts the directory.** Cross-signing stops the server from adding a device to an identity that a client has already pinned or verified. When a client looks someone up for the first time, though, the server can answer with an identity of its own (a "ghost user"). ADR-0016's sentence "The server cannot silently add devices to a user" therefore holds only for identities a client already knows.

Facts verified on 2026-10-14:

- RFC 9420 §12.4.3.2 lets a joiner use an external commit to "resync", replacing "a member's prior appearance with a new one", and §12.2 allows such a commit at most one Remove proposal, with which the joiner removes an old version of itself; the application must check that the joiner's credential is acceptable for the member it removes. OpenMLS 0.9.0, the pinned version, builds external commits (`ExternalCommitBuilder`), always in public framing, so the server's validator can check them, and leaves the identity check to the application (its `validation.rs` says so).
- Apple's documentation ("Supporting passkeys") requires an app to have an associated domain for a relying party before it can use passkeys for it. A desktop app therefore cannot use the platform's passkey interface for any self-hosted server's domain; the system browser can.
- The IETF's key transparency protocol is still an Internet-Draft (draft-ietf-keytrans-protocol-04, April 2026).
- WebAuthn's PRF extension is available in current browsers and on Windows Hello since February 2026 (ADR-0016, context of 2026-10-03).

## Decision

1. **Three signing keys per account, all Ed25519** (threat model §5.1):
   - The **identity key** says who the user is. Its private part is kept only in the account's secret store (item 6) and, briefly, in the memory of a device that uses it; it is used rarely: to certify the device-signing key when the account is created, after a device loss, and in a recovery.
   - The **device-signing key** says which devices belong to the user. The identity key certifies it. Every approved device holds it, wrapped at rest with a keychain-protected key (SEC-11), so that any approved device can approve a new one (COL-13). This refines ADR-0016 Decision 6: the identity key "cross-signs" device keys through this one intermediate key, so that a lost device costs a rotation of the device-signing key, which contacts see as a change of devices, not a change of identity.
   - Each **device key** is the device's MLS signature key, certified by the device-signing key. Under a separate signing label it also proves the device to the server on every connection (item 4).
2. **Credentials carry the chain.** Every MLS leaf's credential names the account and the device and carries the device certificate, the device-signing key's certificate and the identity public key. The server's validator and every client check the chain wherever a leaf appears: in key packages, commits, Welcomes and recovery joins. The Phase-3 work package chooses the encoding (a private-use MLS credential type or X.509) and specifies the byte formats and signing labels; the spike's basic `user/device` credentials are not used in production.
3. **The directory and trust in contacts.** The server publishes, per account, the identity public key, the device-signing certificate and a signed device list with a version number, the current devices and the revoked ones. Clients pin a contact's identity key the first time they see it, refuse a device list older than one they have seen, and stop with a warning before sending anything new to a contact whose identity key has changed. Users can compare safety numbers or scan QR codes and then see the contact as verified. A user's own pins and verifications travel in the user's encrypted settings and key backup, so a new or recovered device does not start trusting the directory afresh. The server can still answer a lookup for someone a client has never seen with an identity of its own; this is stated as a residual risk (threat T23), and key transparency is evaluated at the Phase-3 gate.
4. **Devices are approved by comparing keys.** A new device registers as pending after signing in; until it is approved it cannot read group data, claim key packages, publish, end other sessions or delete anything. An approving device authenticates the new device's keys out of band, by scanning a QR code the new device shows or by both devices showing the same short code from a commit-then-reveal exchange, then certifies it and sends it the device-signing key sealed with HPKE to a one-time key of the new device. A bare "Approve?" button is never offered. Administrators can additionally require their own approval (COL-13); that is a gate on the server, not a certificate. Sessions belong to devices, and every connection and every security-relevant request carries the device key's signature on a fresh challenge from the server, as DPoP (RFC 9449) does for OAuth tokens.
5. **The recovery kit is a generated secret.** The account's first device generates a random 256-bit recovery secret, shows it as words and a QR code, asks the user to confirm part of it, and never stores it. It is never a passphrase chosen by the user: a passphrase would need a password-hashing function such as Argon2id, which MLS's providers do not include (ADR-0016 Decision 12).
6. **The secret store.** A key derived from the recovery secret with HKDF seals the identity key, the device-signing key and the key-backup key with an AEAD under a 256-bit key, bound to the account; the server keeps only this ciphertext and its version, and a device may read it during a recovery.
7. **The key backup.** Every device of the user seals the latest snapshot key of each of the user's documents, with HPKE using the production ciphersuite's hybrid post-quantum KEM, to the account's key-backup public key, and stores it on the server. A recovered device can then read the latest snapshot of every document, including documents nobody else holds. The server learns only that a backup entry exists for a group.
8. **Recovery joins** (this changes design detail 3 of ADR-0016's amendment of 2026-10-07 in one point). An approved device of a user who has a role in a group may join that group by an MLS external commit, without another member's help, if: its credential chains to the user's identity key; it appears in the user's latest signed device list; the commit removes exactly one existing device of the same user and no one else; the roster does not change; and the session that sends it signed in within the last few minutes. The server's validator and every client check all of this, and clients show members that the user rejoined after a recovery. A recovery join by a user who is not an owner takes effect only after a witness confirms it (ADR-0030). Members publish the group information that external commits need, with each commit. The same mechanism serves devices that fell behind the server's log retention and devices left behind after a dispute (ADR-0030). After rejoining, the recovered device removes the user's remaining old devices with ordinary own-device removals.
9. **Passkey unlock is opt-in.** A user may wrap a copy of the recovery secret with a key derived (HKDF) from a passkey's PRF output, bound to the credential ID and the account; switching it on needs the recovery kit once, and administrators can switch the feature off for their organization. The desktop app uses the platform's passkey interface where the platform allows it for the server's domain, and the browser otherwise. The app tells the user that with passkey unlock, whoever can use the passkey, including through its sync provider, can both sign in and unlock the account, and that in a browser the server's code sees the unlocked secret (threat T11). It is never the only path (ADR-0016 Decision 7).
10. **Device loss.** From any remaining device, the user publishes a new signed device list revoking the lost device; the server ends its sessions and refuses its connections at once; the user's devices remove it from every group with MLS commits; and, because every approved device holds the device-signing key, the user then rotates that key with the recovery kit or passkey unlock and re-certifies the remaining devices. Without a remaining device, the user recovers (items 6–8).
11. **Cryptography.** Everything here uses Ed25519, HKDF, AEAD and HPKE, including the hybrid KEM, as provided by OpenMLS's crypto provider; no other primitive, no password hashing and no password-authenticated key exchange is used (ADR-0016 Decision 12). The Phase-3 work package that builds it specifies every byte format, label and associated data, with test vectors.

## Consequences

- A user who keeps the recovery kit gets back their identity and every document after losing all devices, and a document whose only owner lost every device can be managed again.
- A sign-in taken over through an identity provider, a passkey or an administrator does not give keys or a trusted device.
- The recovery kit becomes the root of the account: whoever holds it and can sign in owns the account (threat T28). Recovery joins are visible to every member, which makes their abuse noticeable but not impossible (T39).
- The server stores three new kinds of ciphertext (secret store, key backup, passkey wraps) and the directory; the threat model's metadata inventory (§9) lists them.
- The validator and every client must check credential chains, device lists and recovery joins; the Phase-1 server work packages prepare for it (device-bound sessions, pending devices) and Phase 3 builds it.
- At first contact without verification, users still trust the server's directory, until key transparency.

## Alternatives considered

- **The identity key on every approved device:** one key fewer, but a stolen device could certify devices until the user replaced the identity key itself, which every contact would see as a new identity and have to re-verify.
- **The identity key needed for every approval:** the recovery kit at every new device; contradicts COL-13's approval from a trusted device and trains users to type their kit often.
- **Owners re-add a recovered user instead of recovery joins:** leaves documents whose only owner lost every device frozen for good, and documents only the user held unreadable.
- **A passphrase instead of a generated kit:** needs a password-hashing function outside MLS's providers (an ADR and an expert review under ADR-0016 Decision 12) and lets the server try guesses against the stored ciphertext.
- **Recovery held partly by the server, or by friends (secret sharing):** the first breaks the zero-knowledge invariant (ADR-0015 Decision 6); the second needs secret sharing, which MLS's providers do not include, and a design of its own.
- **Approving with a short code typed on the other device:** without a password-authenticated key exchange, the server can guess such a code offline and approve its own device.
- **Key transparency now:** the IETF protocol is still a draft and no implementation has been chosen; re-evaluated at the Phase-3 gate.

## Validation gate

The Phase-3 work package that builds identity and recovery (epic E3-DEVICES-KEYS in [plan/05](../plan/05-work-breakdown.md)) must show, natively and in WebAssembly, with tests: chains checked by the validator and by clients, including refusal of a broken or revoked chain; approval refusing a pending device whose keys differ from the scanned or compared ones; recovery on a new device that rejoins a document whose only owner was the recovered user, and a private document read from the key backup; refusal of a recovery join that removes another user's device, removes nothing, changes the roster, or comes from a revoked device; and device loss followed by rotation of the device-signing key. An expert review of the constructions precedes it; the external audit (SEC-08) follows it.

## Revisit when

The IETF publishes key transparency or an audited implementation fits the stack; post-quantum signatures are adopted (ADR-0016, amendment 2026-10-04); MLS's extensions (draft-ietf-mls-extensions) are published; platforms let apps use passkeys for any domain; the expert review or the external audit asks for changes.
