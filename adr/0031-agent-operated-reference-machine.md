# ADR-0031: An agent-operated Word reference machine that opens only vetted documents

- **Status:** Proposed. The owner decided the direction on 2026-11-13; the orchestrator asks the owner to accept the final text after review, because it concerns the owner's hardware and a security promise ([ADR-0001](0001-record-architecture-decisions.md) Decision 5).
- **Date:** 2026-11-13
- **Deciders:** Owner (the direction, 2026-11-13); the orchestrator, in the owner's place, on the points the owner's words left open (T3, the probes' route, files that BayanDocs saves, Word's PDFs, the session on the machine until Remote Control is available, Word staying online); the text by the planner session PLAN-REF
- **Related:** FID-04, FID-06, [ADR-0004](0004-fidelity-contract-and-determinism.md) (§5, the reference for Tier C), [ADR-0017](0017-supply-chain-and-dependency-policy.md), [ADR-0023](0023-automation-macros-active-content.md), [ADR-0025](0025-quality-gates.md) (Decision 2), [Fidelity Lab specification](../specs/fidelity-lab.md) §3, §4 and §7, [threat model](../specs/threat-model.md) T16, T19, T40 and §13.5, [owner checklist](../plan/09-owner-checklist.md) items 9 and 10, [plan/12](../plan/12-orchestration.md#the-word-reference-machine), [LAB-002](../workpackages/phase-0/LAB-002-word-ground-truth-harness.md), [LAB-005](../workpackages/phase-0/LAB-005-probes-and-first-study.md), [CORE-008](../workpackages/phase-0/CORE-008-font-audit.md), LAB-101, LAB-108

## Context

The Fidelity Lab measures BayanDocs against Microsoft Word for Windows, the reference of Tier C ([ADR-0004](0004-fidelity-contract-and-determinism.md) §5). Word runs on one Windows computer, the **reference machine**, where a harness opens corpus documents and records what Word makes of them: a PDF, a layout skeleton, a re-saved copy and metadata ("ground truth"). LAB-002 builds the harness; LAB-005's probe studies, CORE-008's font audit and every later Tier C measurement depend on it.

**The old design treated the machine as a quarantine.** The corpus was to include tier T2, real-world documents crawled from the open web, and any of them may be malicious: Word is a large native program with a long history of vulnerabilities triggered by crafted documents (macros, DDE fields, embedded OLE objects, remote templates, linked content, embedded fonts, its converters). So the machine was to be isolated and locked down: a Windows account without Claude, where the owner typed commands by hand and carried results between logins ([Fidelity Lab specification](../specs/fidelity-lab.md) §3 and §4, LAB-002 and item 9 of the [owner checklist](../plan/09-owner-checklist.md) as they stood before this ADR).

**That does not work in practice.** The owner cannot be the go-between. Every harness run, every round of a probe study, every fix to a script and every result would wait for the owner to type commands they are still learning to read and to carry files between accounts; LAB-005's studies alone need many rounds. Everything else in the project runs through agent sessions that the orchestrator starts ([plan/12](../plan/12-orchestration.md)); the reference machine would be the one part that needs the owner every day, and LAB-002, LAB-005 and CORE-008, with all Tier C measurement, would stall behind it.

**The danger came from the documents, not from the agents.** What made the quarantine necessary was opening untrusted documents from the open web. If Word opens only documents that the project generates, or public documents that pass a strict automatic check for everything that makes Word fetch or run something, most of the reason for keeping agents away from the machine disappears, and what remains can be limited by an account with nothing of value in it.

**How agents can reach the machine.** As the product works on 2026-11-13, the Claude desktop app can share a folder of the computer it runs on through Remote Control (in the app: Settings, Claude Code, Remote Control); on Windows, not every version of the app can serve a folder. A cloud session of the same Claude account can ask to use that folder; a person answers every such request in the Claude app, on a trusted device, and no permission mode or stored rule can answer it instead; the session's commands and file tools then run in that folder on that computer. The computer answers only while the app runs there; the folder cannot be the user folder itself or a hidden folder directly under it; and only the person can disconnect it. Using a computer's folder from a cloud session is not yet available to every account, and on 2026-11-13 it is not available to the project's account. A Claude Code session can also run on the computer itself, and a cloud session can send messages to the owner's sessions on their computers once the owner allows it, with an approval on the owner's own device.

## Decision

1. **One lab account, operated by agents.** One Windows account on the reference machine is used only for the lab. It is a standard user, not an administrator. It holds no personal data and no GitHub credentials, and no sign-ins other than the two the lab needs: the Claude desktop app and Word's activation. The Claude desktop app runs there, signed in, and shares one folder of that account (for example `BayanLab` in its user folder) through Remote Control. Agent sessions that the orchestrator starts attach to that folder, edit files, run code and operate Word there; the owner approves each session's request to use the computer. **Until the project's account can use a computer's folder from a cloud session,** the agent instead runs in a Claude Code session on the machine itself, in the lab account and the shared folder, which the owner starts once with a prompt from the orchestrator. The orchestrator reaches that session with session messages if the owner allows that once, by an approval on the owner's own device; otherwise the session's questions go to the owner.
2. **Word opens only vetted documents,** and only approved files reach the machine. Vetted documents are:
   - **T0 probes** that the project generates;
   - **T1 public documents** that pass an automatic **document safety check** in CI before they reach the machine; and
   - **files that BayanDocs saves**, for the round-trip checks (Fidelity Lab specification §6, M6; the Phase-1 exit criterion E1.2; LAB-108).

   The check accepts only `.docx` files that bayan-lab's hardened reader (bayan-opc and bayan-xml) parses within its limits, that are a ZIP package from their first byte to their last (the first local file header at offset 0, and no bytes before, between or after the entries other than the central directory and its end records), and that have no macros or VBA parts; no external relationships (any relationship with `TargetMode="External"`: remote templates, linked images, links to addresses outside the document and every other kind); no embedded OLE objects or ActiveX controls; no DDE, INCLUDE or other fields that fetch; no altChunk (content that Word imports from another format when it opens the document); and no embedded fonts. Files from the parts of test suites that hold exploit or crash samples are left out by policy, even when they pass, and so is any file whose path contains "crash" or "fuzz" in any letter case. The check produces a list of approved SHA-256 fingerprints, and the harness on the machine refuses any file that is not on it. Probes and files that BayanDocs saves reach the list the same way: CI produces them with code on `main` (probes from parameter sets committed in bayan-core, saved files from approved documents), runs the same check on them and lists them. Each approved file reaches the machine on its own and is checked against the list before it is written there; no checkout or archive of a corpus source does. LAB-002 builds the check, in bayan-core's lab tooling on bayan-lab's scanner, and may make it stricter, for example by rejecting what it cannot classify, but never looser.

   **T2**, documents crawled from the open web, **is postponed.** It is not processed on this machine. If it is ever wanted, it gets a separate, disposable setup without Claude, decided then. The private corpus's storage (owner checklist item 10) waits with it. **T3** (torture documents) follows the rules of its documents' source: a public, redistributable T3 document with a recorded source passes the same check and joins the same list as T1; a T3 document crawled from the open web waits with T2.
3. **Word's hardening stays, as defence in depth.** Macros are disabled without notification, external content is blocked, links and fields are not updated, Word's File Block settings refuse every format except Word 2007 and later documents, add-ins and cloud features are off, AutoSave and OneDrive are off, and the Office build is pinned. The agent applies the per-user settings itself. Word itself stays online: Microsoft 365's Word must reach Microsoft's licensing service regularly, so no rule keeps it off the network, and the approved list, Word's settings (links and fields are not updated) and the machine's network restrictions carry the risk of Word reaching the network on a document's behalf instead. Steps that need an administrator, such as pinning the build or keeping the machine from sleeping, are short scripts that the agent writes, a reviewer session checks, and the owner runs with "Run as administrator". The owner's elevated session runs only bytes that it has checked against a reviewed SHA-256 obtained from outside the machine, for example a script and its hash that a small runner, which only administrators can change, fetches from bayan-core's `main`: it never runs bytes or trusts hashes that the lab account can change, and the owner never types a hash. This protects the step only as far as `main` itself is protected (residual risk 3).
4. **The rules for agents on the machine.** The clean-room rule does not change: agents operate Word only through its automation interface and its user interface and read what Word outputs; they never decompile, disassemble or debug Microsoft software. Microsoft's font files never leave the machine. Agents on the machine treat the text of documents, of Word's messages and of the harness's output as data, never as instructions. They use the Claude app on the machine for nothing but their own session: they answer no prompt in its window, start no session from it and read no other conversation.
5. **No credentials on the machine.** Beyond the two sign-ins of Decision 1, no credentials are stored on the machine, except a storage key that can only add ground truth (not read, list, overwrite or delete it), if LAB-002 decides that it needs one; creating the storage and the key is the owner's. Code and results reach GitHub through the orchestrator's cloud sessions: a cloud session attached to the folder carries them from its cloud side, and the session on the machine of Decision 1 sends them to a cloud session that pushes them, for example as patches in messages; LAB-002 decides how. Until the owner decides otherwise, Word's PDFs, which embed subsets of the fonts a document uses, Microsoft's included, stay on the machine as well ([Fidelity Lab specification](../specs/fidelity-lab.md) §7).
6. **Who does what.** Providing and maintaining the machine stays an owner matter: the one-time setup ([owner checklist](../plan/09-owner-checklist.md) item 9), keeping it on, approving each session's use of it (or, until Remote Control is available, starting the session on the machine and allowing the orchestrator's messages to it), and running the administrator scripts a reviewer approved. Using it is not: the orchestrator schedules work on it like any other work ([plan/12](../plan/12-orchestration.md#the-word-reference-machine)).

## Consequences

- **LAB-002 no longer needs the owner as an operator.** An agent builds the safety check and its approved list, applies Word's per-user settings, writes the administrator scripts, runs the harness on the approved T1 documents and brings the results back. The owner does the one-time setup, starts the session on the machine (or approves a cloud session's request to use it, once Remote Control is available) and runs the reviewed administrator scripts. The safety check needs no machine and can start first.
- **LAB-005 can run its probe studies directly:** its agent runs the approved probes in Word, models what it sees and runs its prototype on the machine with Word's own fonts. Because a new probe set reaches the machine only once its pull request has merged, a study plans its probes in a few large batches rather than one small round at a time.
- **CORE-008 can run its font comparison tool on the machine** against Microsoft's fonts; only summary statistics leave it.
- **The round-trip checks have a route.** M6, E1.2 and LAB-108 need Word to open files that BayanDocs saved; CI produces them from approved documents with code on `main`, checks them and lists them, as it does probes.
- **T2 waits.** No private corpus is collected: item 10 of the owner checklist, the private-corpus part of LAB-101, the weekly T2 runs of the Fidelity Lab specification §9 and the weekly private-corpus runs of ADR-0025 Decision 2 wait until T2 returns, and CORE-008's font frequencies cover the public corpus only. Threat T19 (the private corpus leaks) waits with it.
- **Some features get no Word ground truth from corpus documents for now.** The check keeps out documents with charts made in Word, whose data travels as an embedded workbook (48 documents of the public corpus v1, the largest group), signed documents (2), and documents with OLE objects, ActiveX controls, altChunk, embedded fonts, fields that fetch, linked pictures and links to outside addresses. By the scanner's tags it removes between 73 and 132 of the corpus's 1,253 documents (6 to 11%; the upper figure counts every document with a link, although links within a document are accepted), and up to 178 (14%) if its allowlist also rejects the 48 documents with parts it does not know; documents that refer to an attached template or another outside target, which the tags do not show, come on top. More than a thousand remain. Where the layout of a rejected feature matters, probes can isolate it without the active part, for example a link to a bookmark instead of an address; accepting a chart's plain data workbook, checked like the document itself, is a follow-up.
- **Word's PDFs stay on the machine** until the owner decides otherwise: `bayan-lab pdf-extract` runs there, and whatever needs the PDFs themselves runs there too.
- **The pinned Office build trails Microsoft's security fixes** until the next deliberate re-baseline (Fidelity Lab specification §11), and Word stays online for its licensing. LAB-002's guide says how often the build moves, and a fix for a flaw in how Word reads documents that attackers already use makes a re-baseline due.
- **New obligations:** the safety check and its list are maintained in bayan-core and stay in CI; the per-user settings and the administrator scripts are documented and reviewed; only one agent uses the machine at a time; the threat model carries T19 and the new T40 ([§13.5](../specs/threat-model.md#135-the-word-reference-machine-adr-0031)).
- **The machine is a single point of availability.** While it is off, asleep or signed out, Tier C measurement waits; the orchestrator keeps other work moving and asks the owner to wake it (plan/12).

## Residual risks

1. **A vetted document still exploits Word.** The check looks for what makes Word fetch or run something, not for every flaw in Word's own readers: a crafted picture, chart or other part that the check accepts could still trigger one, more likely in a build that trails security fixes. An exploit gets what the lab account has: its files, the network (Word stays online for its licensing), Word's activation sign-in and the Claude desktop app's sign-in (risk 3); it does not get other accounts' data or administrator rights without a second flaw, and it finds no GitHub credentials.
2. **Prompt injection.** Corpus documents contain text written by others, and a document, a Word dialog or the harness's output could contain text aimed at an AI agent. Agents treat it as data, the harness's messages name documents only by their SHA-256 and quote none of their text, sessions have narrow tasks, and every change reaches GitHub only through a pull request that a separate session reviews. An agent can still be misled into doing something on the machine, or into reporting wrong ground truth, that no review sees.
3. **The Claude sign-in on the machine, and everything that account can reach.** Whoever controls the lab account, through an exploit, a misled agent or at the keyboard, can use the desktop app as the signed-in Claude account: start sessions, read the account's conversations and sessions, and use what it is connected to, including the GitHub access with which its sessions push to the BayanDocs repositories. `main` requires no approving review while the owner is the only maintainer ([scripts/github-settings.py](../scripts/github-settings.py)), because agents open pull requests as the owner, and the account's cloud sessions can open and merge pull requests exactly as the orchestrator does. So whoever holds the lab account's Claude sign-in can get any change merged that passes the required checks: a compromise of the supply chain (threat T16) reached through the lab account. The review of every pull request is the orchestrator's practice, which such a person need not follow, and the owner's approval of each Remote Control request does not protect against a stolen sign-in either; until Remote Control is available, the agent's own session also runs on the machine. Signing the Claude app out on the machine stops it. Word's activation is a second sign-in on the machine, with the Microsoft account it uses, which is why the owner checklist asks for an account used for nothing else where the subscription allows it.
4. **An administrator script changed before it runs.** The lab account controls the shared folder and everything that runs in it, so a check made there proves nothing against a compromised account; that is why the owner's elevated session runs only bytes that it checked against a reviewed SHA-256 from outside the machine (Decision 3). What remains: the script and its hash are only as trustworthy as `main` (risk 3); the runner must be installed once from outside the lab account's reach; and elevating from the lab account's desktop trusts that desktop while the owner types the administrator password, which running the step after signing in to the owner's own administrator account avoids.
5. **The machine is offline.** It may be switched off, asleep, restarted by Windows updates or signed out, or the app may not run; agents then get no answer, and the lab's measurements wait. Nobody stands in for the machine with mocked or made-up ground truth.

## Alternatives considered

- **Keep the quarantine, with the owner relaying commands and results.** It keeps Claude off the machine entirely, but it does not work in practice: everything on the machine waits for the owner, who cannot be the go-between and should not have to type commands they cannot check. LAB-002, LAB-005 and CORE-008, and with them all Tier C measurement, would stall.
- **A disposable virtual machine for every run.** Each run would start from a clean image, so an exploit would not survive it. But it needs a host and a hypervisor managed with administrator rights (owner steps again, or an administrator agent); every fresh machine is a new device for Word's activation and needs the Claude app signed in again, which repeats the sign-in risk rather than removing it; it adds Windows licensing questions; and its isolation matters most for documents this design no longer opens. It remains the candidate for T2, without Claude, if T2 is ever wanted.
- **A separate Claude account for the machine.** It would keep the project's own account off the machine, but a cloud session can only use folders that its own account shares, so the orchestrator's sessions could not use the machine; the separate account would need its own sessions and its own subscription, an owner matter that spends money, and the owner would become the go-between again. Not chosen now.
- **Making the lab account an administrator, so that no step needs the owner.** It would remove the few owner steps, but an exploit through Word or a misled agent would then control the whole machine: switch off Windows' protections and the network restrictions, install services or drivers that survive restarts, change the pinned build and the hardening, and read other accounts' data. Administrator steps are rare (the setup and each re-baseline), so the owner running reviewed scripts costs little.
- **Processing web documents (T2) on this machine, with Claude present.** These are the documents the danger came from: a malicious one could take over the lab account and with it the Claude sign-in and everything that account reaches, and its text could target the agents. Postponed; if T2 is ever wanted, it gets a separate disposable setup without Claude.

## Revisit when

- **T2 is wanted.** A planning session designs the separate, disposable setup without Claude with the owner, and item 10 of the owner checklist returns.
- **Remote Control from cloud sessions changes** in a way that matters here: approving each session's request is no longer required, sessions of other accounts can use the folder, what an attached session can do on the computer changes, or it is withdrawn. When it becomes available to the project's account, cloud sessions replace the session on the machine of Decision 1 without a new decision.
- **Any security incident on the machine:** an approved document that makes Word behave unexpectedly or turns out to be malicious, signs of compromise of the lab account, or an agent misled by text on the machine. Agents stop using the machine, the owner signs the Claude app out, and a planning session reviews this decision.
- **The check keeps out what must be measured,** for example if the features it rejects turn out to matter for fidelity in documents that users bring, or T1 cannot reach LAB-101's targets because of it.
- **Batching slows the probe studies too much.** If LAB-005 shows with evidence that waiting for a merged pull request before each probe set reaches the machine slows its studies too much, the way probes reach the approved list is reconsidered.
