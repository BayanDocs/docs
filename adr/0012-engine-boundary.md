# ADR-0012: Engine boundary — JSON message protocol, C ABI and WebAssembly

- **Status:** Accepted
- **Date:** 2026-10-03
- **Deciders:** Planner
- **Related:** ARC-03, ARC-07, ARC-08, [specs/engine-protocol.md](../specs/engine-protocol.md), CORE-007, DESK-002, WEB-002

## Context

Two shells in different languages (C++/QML and TypeScript) must drive the same engine with identical behavior. On the web, the engine must run in a Web Worker (to keep the interface responsive), so calls cross a `postMessage` boundary anyway. On desktop, it runs on its own thread. We want the boundary narrow, versioned, easy to log and replay, and light on dependencies in all three languages.

## Decision

1. **A message protocol** is the only interface between shells and engine: commands, queries and input events in; responses and events out; plus host-service requests from engine to shell. Messages are **JSON**, defined once as Rust types (serde) in `bayan-engine`, with a **JSON Schema** generated for every release and **TypeScript types** generated for the web shell. QML consumes messages natively as JavaScript objects; C++ uses Qt's built-in JSON classes, so the desktop needs no extra serialization library.
2. **Binary channels** carry bulk data outside JSON: file bytes, font bytes, images, clipboard payloads and tile pixels, referenced from messages by blob identifiers. On the web, blobs are transferable `ArrayBuffer`s and tiles are transferable `ImageBitmap`s.
3. **Desktop binding:** a small C ABI in `bayan-ffi` (header generated by cbindgen) with roughly ten functions: create and destroy an engine, post a message, register an event callback, put and get blobs, render a tile into a caller-provided buffer, and version queries. The engine owns its thread; callbacks run on the engine thread and the shell marshals them to the Qt main thread.
4. **Web binding:** `bayan-wasm` (wasm-bindgen) plus a small worker host script that relays messages between the main thread and the engine. The main thread never calls the engine directly.
5. **The engine never touches the outside world itself**: system fonts, clipboard, network transport, timers, opening URLs, AI inference and file access beyond provided blobs are host-service requests the shell fulfils or refuses.
6. **Versioning:** an integer protocol version negotiated in a `hello`/`welcome` handshake, plus the core's semantic version. Within a protocol version, changes are additive only.
7. **Record and replay:** the engine can record every inbound message and host response (with timestamps) to a local file, and replay it on any platform to reproduce a session exactly. Recordings contain document content, so they are created only on explicit request and never uploaded automatically.

## Consequences

- Both shells program against one contract; parity is easier to verify.
- No serialization dependency is added to the desktop or web shells.
- JSON costs microseconds per message at interactive rates; bulk data never goes through JSON.

## Alternatives considered

- **Protocol Buffers:** strong schema tooling and an LGPL Qt module exists, but adds code generation and runtime libraries in three languages for little gain at our message rates.
- **FlatBuffers or Cap'n Proto:** zero-copy, but awkward ergonomics and extra dependencies.
- **Typed foreign-function bindings (Diplomat, cxx, UniFFI) instead of messages:** good for direct calls, but the Web Worker boundary still needs serialization, and record/replay is harder.
- **CXX-Qt (Rust objects exposed to QML):** attractive, but version 0.10 is still in early development with frequent API changes.

## Revisit when

Profiling shows JSON encoding or decoding above 1 ms per frame on a hot path; then switch the encoding to CBOR (supported natively by Qt and by Rust's serde ecosystem) without changing message shapes.
