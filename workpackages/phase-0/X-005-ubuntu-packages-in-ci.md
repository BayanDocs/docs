## Context

Some CI jobs install Ubuntu packages: libraries, and the development files of libraries ("-dev" packages: the headers and link files a compiler needs), that a build or the tests need and that GitHub's runner image does not carry. They take them from snapshot.ubuntu.com, which serves Ubuntu's package archive as it was at a fixed moment, so that every run gets the same versions, signed by Ubuntu (ADR-0017). At today's `main` branches (docs `b05b966`, bayan-desktop `a59bea6`, bayan-web `130bf57`; bayan-server `4c5ea45` and bayan-core `4ff6165` install no Ubuntu packages) there are three such places:

- **bayan-desktop:** the two Linux jobs of `.github/workflows/ci.yml` ([line 57](https://github.com/BayanDocs/bayan-desktop/blob/a59bea602d1df30d47dd9aa863a7e0c52b9cdc9e/.github/workflows/ci.yml#L57) and [line 102](https://github.com/BayanDocs/bayan-desktop/blob/a59bea602d1df30d47dd9aa863a7e0c52b9cdc9e/.github/workflows/ci.yml#L102)) and the C++ analysis job of `.github/workflows/codeql.yml` ([line 162](https://github.com/BayanDocs/bayan-desktop/blob/a59bea602d1df30d47dd9aa863a7e0c52b9cdc9e/.github/workflows/codeql.yml#L162)) run `apt-get update --snapshot "$UBUNTU_SNAPSHOT"` and `apt-get install --snapshot "$UBUNTU_SNAPSHOT" $UBUNTU_PACKAGES`: six -dev packages that Qt needs (`libgl-dev libegl-dev libvulkan-dev libxkbcommon-dev libfontconfig-dev libdbus-1-dev`), at `UBUNTU_SNAPSHOT: 20261027T000000Z`. [tests/workflows/test_ubuntu_packages.py](https://github.com/BayanDocs/bayan-desktop/blob/a59bea602d1df30d47dd9aa863a7e0c52b9cdc9e/tests/workflows/test_ubuntu_packages.py) keeps the two workflows' values equal.
- **bayan-web:** `scripts/dev-setup.sh` ([`APT_SNAPSHOT=20261025T000000Z`](https://github.com/BayanDocs/bayan-web/blob/130bf5752dec081a3ad6ae5fc2b11a0a35809a77/scripts/dev-setup.sh#L30) and [`setup_browser_libraries`](https://github.com/BayanDocs/bayan-web/blob/130bf5752dec081a3ad6ae5fc2b11a0a35809a77/scripts/dev-setup.sh#L286)) installs those of 79 libraries that the Playwright browsers need and that the machine lacks. CI's `pnpm verify (ubuntu-24.04)` job runs it ([ci.yml, line 86](https://github.com/BayanDocs/bayan-web/blob/130bf5752dec081a3ad6ae5fc2b11a0a35809a77/.github/workflows/ci.yml#L86)), and so do developers and, when bayan-web is attached to a session, the agent environment.
- **docs:** [scripts/cloud-environment-setup.sh](../../scripts/cloud-environment-setup.sh) (`step_apt`) installs the same six -dev packages and ShellCheck in the agent environment, at `APT_SNAPSHOT=20261003T000000Z`.

The [dependency update runbook](../../developer/dependency-update-runbook.md) asks to keep the four dates equal. Today they differ (2026-10-27, 2026-10-25 and 2026-10-03), because bayan-desktop moved its date twice outside the monthly session ([bayan-desktop#8](https://github.com/BayanDocs/bayan-desktop/pull/8), [bayan-desktop#9](https://github.com/BayanDocs/bayan-desktop/pull/9)) and left the others to the next monthly session.

### How it fails

Between 2026-10-04 and 2026-11-05, 21 of the 198 attempts of these install steps failed (the orchestrator's count from the Actions API; re-runs count as attempts), for two reasons.

**1. The runner image is newer than the frozen date ("skew"): 8 failures, all in bayan-desktop.** GitHub rebuilds its `ubuntu-24.04` image about once a week with Ubuntu's security updates: 11 versions from 20260810 to 20261026, by the [history of the image's readme](https://github.com/actions/runner-images/commits/main/images/ubuntu/Ubuntu2404-Readme.md). A -dev package requires exactly the version of its library that was current at the frozen date. When the runner already has a newer, fixed version of the library, apt would have to downgrade it, refuses, and stops with "unmet dependencies":

- `libfreetype-dev : Depends: libfreetype6 (= 2.13.2+dfsg-1ubuntu0.1) but 2.13.2+dfsg-1ubuntu0.2 is to be installed`, in both Linux jobs of a pull request on 10-17 (run `39055195605`, attempt and re-run), in the C++ analysis of the same pull request, and in the weekly C++ analysis of 10-20 and 10-27;
- `libbrotli-dev : Depends: libbrotli1 (= 1.1.0-2build2) but 1.1.0-2ubuntu0.1`, in the weekly C++ analysis of 11-03 (run `41654130562`).

Downgrading the library is not an option: it would remove security fixes. This planning session reproduced the failure in a container: on the `ubuntu:24.04` image of 2026-10-25, the snapshot of 2026-10-03 fails with `zlib1g-dev : Depends: zlib1g (= 1:1.3.dfsg-3.1ubuntu2.2) but 1:1.3.dfsg-3.1ubuntu2.3 is to be installed`, while the snapshots of 2026-10-25 and 2026-10-27 install. Runtime libraries are exposed too, only less often: the 385 packages that bayan-web's 79 libraries bring into a bare Ubuntu image include 56 dependencies on an exact version, such as `libpam-systemd` on `systemd (= 255.4-1ubuntu8.18)` and `systemd` on `libsystemd0` of the same version; bayan-web has escaped so far because it installs only what the runner lacks.

The agent environment carries the same risk. Its image (Ubuntu's minimized image, serial 20261024.1, with packages added on 2026-10-27) already holds the security updates of FreeType, zlib and Brotli, together with their -dev packages. The setup script's snapshot of 2026-10-03 still worked there on 2026-11-03 only because none of the packages it had to install depended on the exact versions of those libraries.

**2. snapshot.ubuntu.com is down: about 9 failures, mostly in bayan-web.** From about 11:45 UTC on 2026-11-04 until 2026-11-05, with short recoveries, its dated snapshots answered 401, 502 or 503, while archive.ubuntu.com answered normally. bayan-web's install step failed in 7 attempts with apt's `Err:` on the snapshot's InRelease file or metadata:

- the nightly runs of 11-04 and 11-05 (`41826136179`, `42025815758`);
- the run on `main` after a merge, and its one allowed re-run (`41836056589`, attempts 1 and 2);
- a pull request on 11-04 (`41823795008`);
- earlier, with the snapshot of 2026-10-03, a pull request on 10-14 (`38570537024`, attempt 2) and the nightly run of 10-10 (`38045414556`).

In bayan-desktop the sanitizer job got a 503 on 10-14 (`38526184743`), and the C++ analysis of the same push failed in the same minute (its log is gone). bayan-web's step also failed 3 times without a log left (10-11, 10-14, 10-20), and once because Playwright's download server could not be found (10-21), which is not Ubuntu's doing. Running the jobs in a container alone (option A below) does not help here, because the container would still download from the snapshot.

Successful install steps take, as medians: 59 s in bayan-desktop's Linux jobs (at most 303 s, 77 steps), 92 s in its C++ analysis (336 s, 22 steps), and 158 s for bayan-web's whole set-up step, which also installs Node.js, pnpm and the browsers (1047 s, 75 steps).

### The design

Two changes remove the two failure modes, and a cache makes the second one rarer still.

1. **A pinned base.** Each Linux job that installs Ubuntu packages runs in a container (`container:` in the workflow), started from an image: the job's steps then use the image's own file system and packages, independent of the runner image. The image is a Docker Official Image of Ubuntu 24.04 pinned by its digest (the SHA-256 of its contents, so the same reference always gives the same image): `docker.io/library/buildpack-deps:noble-scm@sha256:…`, Ubuntu's own image plus tools such as ca-certificates, curl and git, so that a job can check out its history and download over HTTPS before anything else is installed. The packages are installed on this fixed base instead of the runner image, so a newer runner image changes nothing. The snapshot date is chosen on or after the base image's creation, and the monthly session moves the base and the date together. This is option A of bayan-desktop#9's follow-up. The container is not a sandbox: GitHub's runner mounts its Docker socket into job containers, so a program that runs as root in one can control the runner. It changes what the job's packages are, not who can affect the runner.
2. **Exact files, from more than one source.** Each repository commits a lock file, which the monthly session generates by running apt in the pinned base against the snapshot. It lists every package file to install, with its path in Ubuntu's archive (the "pool"), its size and its SHA-256, all taken from the package index that apt has verified against Ubuntu's signature with the base image's own keyring, and the order in which apt would unpack and configure them. Until now apt checked that signature on every CI install; from now on the lock's hashes are the link to it, so they come from nowhere else. In CI, the files are first fetched: each one is downloaded and its size and SHA-256 checked. Because the hash proves the file, its source does not matter: the fetch tries the snapshot at the lock's date first, then Launchpad's librarian (the file store of Launchpad, the service that builds Ubuntu's packages, which keeps the files of the packages Ubuntu has published), then the live archive. It moves to the next source only when a download fails, and stops at the first mismatch without trying another source, as bayan-core's [spike fonts](https://github.com/BayanDocs/bayan-core/blob/4ff61658a48bc07d3c5f9062a903044a7de80bff/spikes/text-pipeline/fonts/fetch.sh#L50) do. Then the files are installed with dpkg, Debian's low-level package tool, in apt's recorded order, without apt, without a package index and without network.
3. **A cache of verified files.** `actions/cache` keeps the fetched files between runs, keyed by the lock file's hash. A job restores the cache, fetches what is missing, saves the cache, and only then installs, so the cache holds only checked files, saved before any package's installation program has run. Runs on `main` save it; pull requests and the merge queue only read it, and every file taken from it is checked like a download. Between two changes of the lock, runs then need no Ubuntu server at all.

No rule of ADR-0017 is loosened. The base is pinned by digest and at least a day old; every file is pinned by SHA-256 in the repository and older than the session's cutoff, because it was in the archive at a snapshot date before the cutoff; nothing is chosen at run time, by apt or by anyone else. The packages' maintainer scripts (the programs a package runs while it is installed) still run, as they did under apt; rule 6 asks for such an exception to be named, and the amendment names it, now limited to exactly the locked files. The [amendment of 2026-11-05 to ADR-0017](../../adr/0017-supply-chain-and-dependency-policy.md#amendment-2026-11-05-ubuntu-packages-in-ci), proposed together with this brief, records the decision. As a change to the supply-chain policy it needed the owner's explicit confirmation ([ADR-0001](../../adr/0001-record-architecture-decisions.md), rule 5); the owner confirmed it on 2026-11-12, and it is Accepted.

### What was measured

This planning session measured the design on 2026-11-05 with Docker in the BayanDocs cloud environment, where downloads go through the session's network proxy, which is slower than GitHub's network:

| | bayan-desktop | bayan-web |
|---|---|---|
| Requested packages | the six -dev packages, plus python3-venv, g++, xz-utils, zstd and rustup, which the runner image provided until now | the 79 browser libraries, plus unzip and xz-utils |
| Lock on `buildpack-deps:noble-scm` (created 2026-10-26) at the snapshot of 2026-10-27 | 123 files, 138.5 MB | 366 files, 218.6 MB |
| Downloading the files one after another, each checked | 113 s | 423 s |
| Installing them in a container without network, in apt's recorded order | 11.4 s (2 dpkg calls) | 28.6 s (4 dpkg calls) |
| Disk used, base image included | 917 MB | 1214 MB |

- **The order matters.** One `dpkg -i` call with all files is not enough: it configures packages only at the end, and `systemd-sysv` must not be unpacked before `systemd` is configured (a pre-dependency), so the web set fails. `apt-get install ./*.deb` without a package index stops with `E: Internal Error, Pathname to install is not absolute`. Replaying apt's own plan (the `Inst` and `Conf` lines of `apt-get -s install`) as batched `dpkg --unpack` and `dpkg --configure` calls installs both sets with `dpkg --audit` reporting nothing; gcc 13.3, Python's venv and rustup 1.26 then work.
- **The sources.** Of the 483 package files of both sets at the snapshot of 2026-10-27, all are on Launchpad, and all but 2 (libsoup 3.4.4-5ubuntu0.9) are still in the live archive nine days later. For a lock one month old (the same packages at the snapshot of 2026-10-03), 36 files had changed by 2026-10-27 and 27 are no longer on archive.ubuntu.com, but all 483 are on Launchpad and on the snapshot. The live archive is therefore only a last resort, and Launchpad is the real second source.
- **The base.** `buildpack-deps:noble-scm` (digest `sha256:94ed690dd634b8b2f531eaa742fde9b1264077cd8ea695a3b960bd104ae4c481`, created 2026-10-26 at 23:50 UTC, tag last updated 2026-11-03) is 89 MB compressed, which every container job downloads from Docker Hub, and 262 MB on disk. It is built on the same Ubuntu image (serial 20261024.1) as `ubuntu:24.04` (digest `sha256:fe81560990fae86dc4743202b2cb4d3df98d0bcf949173cecef15ce1127ef852`, created 2026-10-25, 30 MB compressed), which has no ca-certificates, curl or git. mirror.gcr.io serves the same digest.
- **A prebuilt image** with the packages already installed would be about 250 MB (bayan-desktop) and 340 MB (bayan-web) compressed, measured on `ubuntu:24.04` with apt (724 MB and 908 MB on disk).

### What else was weighed

- **Option A alone** (a container, with the packages from the snapshot through apt): it removes skew but not outages, and each job would also download its compilers and tools from the snapshot. It is part 1 of the design.
- **A prebuilt image** with the packages installed, built from the pinned base, the snapshot and the package list, and pinned by digest: no Ubuntu server at run time at all. A workflow in each repository would build it and store it in GitHub's container registry (`ghcr.io/bayandocs/…`), with GitHub's artifact attestations to show its provenance, which the session that records the digest checks with `gh attestation verify`. But publishing a package and its registry settings are the owner's ([plan/12](../../plan/12-orchestration.md#what-only-the-owner-decides)); the job that builds the image runs the packages' maintainer scripts, so under the [workflow conventions](../../AGENTS.md#workflow-conventions) it may not hold `packages: write`, and the job that pushes the image would have to run the docker program or a third-party action instead of only GitHub's own actions, which needs the owner too. The image also cannot be rebuilt byte for byte, so a reviewer could check it only through the attestation, while a lock file is a list that anyone can read in a diff. With the cache, the design gets most of the benefit without any of this. Not recommended now; it remains the way forward if downloads ever become the bottleneck.
- **Option B** (keep the frozen date, and fail with a clear message when the runner image is newer): the failure becomes easier to understand but not rarer. It is used only where nothing can be pinned (below).
- **Option C** (take the snapshot date from the runner image at run time): GitHub's image would choose the versions, and the repository would no longer record them, which loosens ADR-0017 and is the owner's decision. The design does not need it.
- **Exact files on the bare runner, without a container:** the -dev packages would still require the old library versions that the newer runner image has replaced, so skew would remain.
- **GitHub's custom runner images** (a pinned virtual machine image of our own): available only for larger runners, which cost money and need organization settings, so the owner's; not needed.
- **Microsoft's Playwright container image** for bayan-web: a third-party build whose browsers and Node.js our pins do not check, and no help for bayan-desktop or the agent environment.
- **Unpacking the -dev packages into a private folder** for the compiler, next to the runner's own libraries: dpkg would check nothing, so no skew, but the build set-up would be unusual and differ from developers' machines.

### Where the current method stays

- **Developers' own Ubuntu machines** (bayan-web's `scripts/dev-setup.sh` outside CI) and **the agent environment** (`scripts/cloud-environment-setup.sh`) keep installing from the signed archive frozen at a snapshot date. Their base belongs to the developer or to the cloud environment, not to the project, and changes without notice, so it can be neither pinned nor locked against in advance. A failure there blocks no pull request: dev-setup stops with apt's message, and the agent environment's setup never blocks a session, lists a failed step in `bayandocs-tools`, and keeps its result for about seven days. The agent environment gets two small changes through [issue #7](https://github.com/BayanDocs/docs/issues/7), the batch of setup-script changes that the docs monthly session applies: the rule for its date (on or after the newest package of its image) and option B's message (see the scope).
- **macOS and Windows jobs** install no Ubuntu packages; neither do bayan-web's engine job and the workflows of bayan-core and bayan-server.

## Objective

In bayan-desktop and bayan-web, no Linux CI job depends on the runner image's libraries, or on one Ubuntu server being up, to install its Ubuntu packages: each runs in a container from a base image pinned by digest and installs exactly the files its repository's lock lists, checked against their sizes and SHA-256 hashes, which come from Ubuntu's verified index, and fetched from the cache, the snapshot, Launchpad or the live archive. The monthly session moves the base image, the snapshot date and the locks together.

## Scope

### In scope

- **Container jobs.** In bayan-desktop, the jobs `linux` and `sanitizers` of `ci.yml` and `cpp-analysis` of `codeql.yml`; in bayan-web, the `ubuntu-24.04` entry of the `verify` matrix of `ci.yml` (the macOS entries stay as they are). Each runs in a container from the same `buildpack-deps:noble-scm` digest, with the image's creation date in a comment. The jobs keep their names, so the required checks stay the same. Container options are added only where a job needs them (for example more shared memory for the browsers, or `--cap-add=SYS_PTRACE` if LeakSanitizer needs it), never `--privileged`. If a simpler base keeps every rule (for example `ubuntu:24.04` with a hash-checked bootstrap of ca-certificates and git), the implementer may use it and says why.
- **The lock**, one per repository (for example `deps/ubuntu-packages.lock`). A header names the base image (reference and digest), its creation time, the architecture (`amd64`), the snapshot date and the requested packages. Then follows apt's plan for that base and date, one step per line: each file to unpack, with its pool path, size and SHA-256, and each package to configure. The requested packages are those the jobs use: today's `UBUNTU_PACKAGES` and `APT_PACKAGES`, plus what the jobs took from the runner image until now (compilers, Python's venv, rustup, zstd, which the CodeQL action needs to unpack its bundle, xz-utils, unzip and whatever else the jobs turn out to need), each listed explicitly, installed with `--no-install-recommends`. The plan also upgrades the base image's own packages that have newer versions at the snapshot date (curl, git, OpenSSL and the CA certificates among them), so that they do not stay at the image's build date until the base moves.
- **One script, identical in both repositories** (for example `scripts/ubuntu-packages.sh`, POSIX shell, clean under ShellCheck, with `DEBIAN_FRONTEND=noninteractive` wherever it runs apt or dpkg), with three commands:
  - `lock`, for the monthly session and for CI's check of the lock (below): runs apt in the pinned base image with Docker. It runs `apt-get update --snapshot <date>` with `https://` sources, which must verify the snapshot's index against Ubuntu's signature with the base image's own keyring, and stops if that check fails: no `[trusted=yes]`, no `--allow-insecure-repositories` or `--allow-unauthenticated`, and nothing similar. It takes each file's pool path, size and SHA-256 only from that verified index (for example with `apt-cache show -o APT::Snapshot=<date>`), never from an index downloaded separately, and the plan from apt's simulated install. It refuses a date earlier than the image's creation or later than a cutoff it is given, and a plan that would remove a package (`Remv` lines). It writes the lock so that the same inputs always give the same file, byte for byte.
  - `fetch`, for CI, before the install: puts every file of the lock into the cache folder. A file that is already there is checked against its size and SHA-256; one that fails the check stops the job, with a message that says how to recover (for example by bumping a version in the cache key in a pull request). A missing file is downloaded from `https://snapshot.ubuntu.com/ubuntu/<date>/<pool path>`, then `https://launchpad.net/ubuntu/+archive/primary/+files/<file name>`, then `https://archive.ubuntu.com/ubuntu/<pool path>`. Every download uses HTTPS only, redirects included, and has a connect timeout and a low-speed or total-time limit (the agent environment's setup script uses `--connect-timeout 20 --max-time 300`), so that a source that stalls counts as a failed download. The next source is tried only after a failed download, never after a size or SHA-256 mismatch, which stops the job and names the file; when every source fails, the job stops and names the file and each source's error. A file is moved into the folder only after its check, and several may download at a time.
  - `install`, for CI, after the cache is saved: replays the plan with dpkg (a run of unpack lines as one `dpkg --unpack` call, a run of configure lines as one `dpkg --configure` call), without apt and without network, ends with `dpkg --configure --pending`, and checks that `dpkg --audit` reports nothing and that every locked package is installed at its locked version. It ends with a summary: how many files came from the cache and from each source, and the time taken.
- **The cache.** The job runs `actions/cache/restore`, then the script's `fetch`, then `actions/cache/save`, then its `install`. actions/cache chooses its compression by whether `zstd` is on the `PATH`, and the compression is part of the cache's version, so a save after the install, which brings zstd into bayan-desktop's container, would never be found by the next restore; saving before the install also means that no package's maintainer script has run before the save. Both actions are pinned at the commit that bayan-core's fuzzing workflow already pins (`55cc8345863c7cc4c66a329aec7e433d2d1c52a9`, v6.1.0), so no new action pin is needed; the key is derived from the lock's hash; only runs on `main` (pushes and scheduled runs) save, never a pull request or the merge queue.
- **CI checks the lock.** Whenever a lock file or the script changes, CI runs the `lock` command again from the lock's header and fails if the result differs from the committed lock, which proves on every update that the lock matches Ubuntu's signed index. This adds no required check, because the rulesets are the owner's: for example a separate workflow with a path filter that is not required, as bayan-core's fuzzing workflow is (a required check that a path filter skips would block merging forever). The orchestrator merges only when every check is green, required or not (plan/12 §5), so it still guards the merge.
- **Tests**, in each repository's gate and test framework (bayan-desktop: Python run by CTest, like `tests/install-qt`; bayan-web: vitest, like `tests/unit/engine-pin.test.ts`):
  - the lock is well formed, its snapshot date is on or after its base image's creation, every unpacked package is configured, and every job that installs it uses the base image of its header (this replaces `tests/workflows/test_ubuntu_packages.py`);
  - `fetch`, against a local server: a failed download moves to the next source; a source that accepts the connection and then stalls moves to the next one within the time limit; when every source fails, the job stops and names the file and each source's error; a size or SHA-256 mismatch stops without trying another source; a redirect to an address that is not HTTPS is refused; a cached file is checked, and a bad one stops the job with the recovery message;
  - the `lock` command refuses a snapshot date before the image's creation or after the cutoff, and a plan with `Remv` lines;
  - in bayan-web, every package of `APT_PACKAGES` in `scripts/dev-setup.sh` is a requested package of the lock, and `APT_SNAPSHOT` equals the lock's snapshot date; without this, a later change to that list (for example with a Playwright update) would make dev-setup quietly fall back to apt and the snapshot in CI.
- **bayan-web's `scripts/dev-setup.sh`** stays unchanged for machines outside the container. In the container, the script's `install` has already installed every package of `APT_PACKAGES`, so dev-setup's library step reports them installed and calls no apt, and the test above keeps it so; it runs as root without sudo (its `as_root` already allows that). `APT_SNAPSHOT` takes the lock's snapshot date.
- **The first lock** of each repository uses the newest base image and a snapshot date chosen by the new rules, both older than the cutoff, and the same in both repositories. This moves bayan-desktop's and bayan-web's pins outside the monthly session, which the orchestrator allows when every rule of ADR-0017 holds (as for bayan-desktop#9); the pull requests state both dates.
- **Documentation**, in the same pull requests (AGENTS.md §5: a change of the dependency posture updates its documents in the same pull request):
  - the [dependency update runbook](../../developer/dependency-update-runbook.md), as described in [The runbook after this work package](#the-runbook-after-this-work-package);
  - the mechanism in bayan-desktop's `AGENTS.md` (its CI bullet describes `UBUNTU_SNAPSHOT` today) and in bayan-web's `AGENTS.md` dependency section, and the header comments of the changed workflows. The "Tools" bullet of AGENTS.md §6 stays as it is: it is identical in all five repositories, and its rule (exact versions, checked against a SHA-256 written in the repository) already covers the locked files.
- **The agent environment:** an entry in [issue #7](https://github.com/BayanDocs/docs/issues/7), in that issue's format, for `scripts/cloud-environment-setup.sh`: (1) `APT_SNAPSHOT` is the locks' snapshot date, and on or after the newest Ubuntu package of the environment's image. In a session, `/var/log/dpkg.log` also holds the setup script's own installs, so the image's newest package is the newest entry before the setup script's apt step. (2) When the apt step fails, its note says whether the snapshot could not be reached or the image has newer libraries than the date (apt's "unmet dependencies" on a newer installed version), and what to do in each case. (3) One retry after a short pause when the snapshot could not be reached, within the script's time limit.

### Out of scope

- Option C, a published prebuilt image, GitHub's custom runner images (each needs the owner), and downgrading libraries.
- The monthly sessions' later moves of these pins, and every other pin (Node.js, pnpm, Qt, the browsers, the actions).
- Changing `scripts/cloud-environment-setup.sh` itself (the docs monthly session applies the issue #7 batch), the shared "Tools" bullet of AGENTS.md §6, developers' machines beyond what is written above, and the macOS and Windows jobs.
- Scanning the locked packages for known vulnerabilities (for example with grype, which can read a container image): a follow-up.

## Notes and pitfalls

- **Docker in a cloud session.** The Docker client is installed but its daemon is not running: start it in the background (`nohup dockerd >/tmp/dockerd.log 2>&1 &`). A container reaches the network only through the session's proxy: run it with `--network host`, give apt the proxy (`Acquire::https::Proxy` set to `$HTTPS_PROXY`) and its certificate bundle (`Acquire::https::CaInfo "/root/.ccr/ca-bundle.crt"`, mounted into the container), and the same to curl. The proxy's port can change when the session restarts.
- **The base's sources use `http://`.** The review of this brief measured that in a cloud session apt then fails with "…InRelease is no longer signed" until the sources are switched to `https://`. Switch them; never answer that error with an option that skips the signature check.
- **apt's names and indexes.** `apt-get --print-uris` URL-encodes parts of file names (an epoch as `1%3a`, `+` as `%2b`, `~` as `%7e`); take paths from the index's `Filename` field. Launchpad's `+files` address takes the pool's file name, which has no epoch. `apt-cache` shows a snapshot's versions only with `-o APT::Snapshot=<date>`; without it, it showed newer versions, without a warning (measured).
- **Order.** Record apt's simulated plan (`apt-get -s install`, its `Inst` and `Conf` lines). One `dpkg -i` with all files fails on pre-dependencies, and `apt-get install ./*.deb` without an index stops with an internal error (both measured, see above).
- **Inside the container.** GitHub mounts the workspace, the runner's Node.js for JavaScript actions and the runner's Docker socket into the container, and steps run as root without sudo. git refuses to work in a repository that another user owns ("dubious ownership"), so steps that run git after the checkout may need `git config --global --add safe.directory "$GITHUB_WORKSPACE"`. Browsers need more shared memory than Docker's default of 64 MB (`--shm-size`, or `--ipc=host`), and Playwright's documentation also recommends `--init`. The CodeQL action unpacks its `.tar.zst` bundle with tar and zstd, and GitHub's documentation lists what code scanning needs in a container. Ubuntu's `rustup` package puts `rustup` and its `cargo` and `rustc` proxies in `/usr/bin` (checked: version 1.26.0); check that `scripts/build-engine-sdk.sh` then installs and uses the Rust version that bayan-core pins, as it does on the runner.
- **WEB-002's measurements** (keystroke latency, frame times, round trips, memory) may shift in a container; compare them before and after (AC-10).
- **Docker Hub** serves the base image before any step runs, so there is no fallback for it inside the job; bayan-server's CI already depends on Docker Hub for PostgreSQL. If pulls fail or are rate-limited, escalate (mirror.gcr.io serves the same digest).
- **Download volume.** Every container job downloads the base image (about 89 MB compressed) from Docker Hub; without the cache it also downloads about 140 MB (bayan-desktop) or 220 MB (bayan-web) of package files. GitHub's cache holds up to 10 GB per repository.
- **One work package, three pull requests.** The script must be identical in both code repositories, so one session writes it once; most of the work is in bayan-desktop (three jobs, among them the C++ analysis and the sanitizers), less in bayan-web, and the docs pull request carries the runbook rows. Size L: three pull requests, a new script with tests in two languages, four jobs moved into containers with slow CI feedback, and the draft pull requests of AC-5 to AC-7. Like every work package of size L, it may span sessions, each ending with a pushed branch and hand-off notes ([plan/06](../../plan/06-agent-workflow.md#session-hygiene)).
- **Scheduling.** This work package should be merged before the monthly dependency sessions of bayan-desktop, bayan-web and docs (the first round is due from 2026-11-13), so that they move the new pins with the new runbook rows. The docs session waits too, for three reasons: plan/12 §7 starts a repository's session only when no other implementation session works in that repository, and this work package works in docs; the runbook's docs row copies the code repositories' pins after their sessions, the snapshot date included; and the docs session applies issue #7, where this work package adds its entry. Only the sessions of bayan-core and bayan-server do not depend on it.

## Escalate if

- A job cannot run in a container without `--privileged` or a capability other than those named above, or CodeQL cannot analyse the C++ build there.
- Docker Hub pulls fail or are rate-limited in CI, or Launchpad or archive.ubuntu.com refuse GitHub's runners.
- A required check's name has to change, or CI's check of the lock would have to be a required check (the rulesets are the owner's).
- A lock cannot be reproduced byte for byte, apt's plan does not install cleanly on the pinned base, or apt cannot verify the snapshot's index with the base image's keyring without an option that weakens the check.
- Any part would need a third-party action, a registry, a published image or a looser rule.
